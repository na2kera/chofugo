# client 実装時に置いた仮定

> `packages/client`（その1）を実装する中で、`design-client.md`・`decisions.md` に答えがなかった場面、または解釈に迷った場面の記録。
> 各項目は「場面 / 置いた仮定 / 理由」の順に書く。判断の基準は、ユーザーの3つの指示（ドット調・情報は最小限・トランプは読みやすく）。遊んでみて、あるいはレビューで見直してよい。

## A. 配線

### A1. 静的ファイルの設定の置き場所
- **場面**: design-client §2 は `packages/server/wrangler.jsonc` に `assets`（`not_found_handling`・`run_worker_first`）を足すとしている。
- **仮定**: `wrangler.jsonc` は変えず、`packages/client/vite.config.ts` で Cloudflare の Vite プラグインの `config` から `assets` を足す。ビルドの出力（`dist/chofugo/wrangler.json`）には両方の設定が入る。
- **理由**: `wrangler.jsonc` に足すと、server 単体の `wrangler dev`（server のテスト）が「`assets` に `directory` がない」（`The assets property in your configuration is missing the required directory property.`）で起動しなくなった。`directory` を client のビルド先にすると、server のテストが client のビルドに依存してしまう。Vite プラグインでは `directory` をプラグインが入れる（Cloudflare のドキュメントのとおり）。

### A2. デプロイの経路
- **仮定**: `pnpm deploy` は client で `vite build` のあと `wrangler deploy` を実行する（ビルドの出力の設定を使う）。`packages/server` で直接 `wrangler deploy` すると画面が含まれないので、README に書いた。
- **実行した結果（2026-11-16）**: ユーザーの確認を得て `pnpm run deploy` を実行し、`https://chofugo.na2kera.workers.dev` に公開した。公開先で確かめたこと：ボット4席で5ゲームの試合が最後まで進む／実際の Chrome でトップ画面からルームを作ってホストとして試合を始める／招待リンクから1席に入り、名前の入力・ロビー・カードを出す・再読み込みで同じ席に戻る／手番を放置すると時間切れで1枚出される（Cloudflare 上のアラーム）／別のサイトの Origin からの `POST /api/rooms` は 403。確かめていないこと：実際のスマホでの表示と操作、休止（hibernation）からの復帰（休止したこと自体を確かめていない）、演出4つの動き、本当の回線断のときの表示、全員不在から30分後にルームが消えること。デプロイ直後の最初の1回だけ `/` が 404 を返した（原因は未確認。その後は 200）。
- **その2・その3の公開（2026-11-17）**: ユーザーの確認を得て `pnpm run deploy` を実行した（コミット 281a873、保存の形式は 4。古い形式のルームは閉じる）。公開先で確かめたこと：大富豪・カスタム（16種 ON）・超富豪のボット4席の試合と、CPU 3席相手の試合が5ゲーム完走し、拒否は0件／心拍を送らずにつなぎ直しを繰り返す席があっても、手番が約37秒ごとに時間切れで進む（decisions §18 の不具合の修正。Cloudflare 上のアラームと心拍の確認で動く）／別のサイトの Origin からのルーム作成は 403、テスト用の機能は閉じている（固定の種は 400、テスト用の経路は 404）／実際の Chrome で、スマホの大きさ（390×700）にした画面からルームを作り、超富豪モードで1位を取り、特権の選択（革命）と使用まで通る（どの場面でも横のはみ出し・44px 未満のボタン・画面の外のボタンなし）。実際のスマホでの表示と操作は、同じ日にユーザーが公開先で遊んで「問題なく遊べた」と確認した。

## B. 時間

### B1. 残り時間のバーの基準
- **場面**: `DeadlineView` には期限の時刻（`at`）しかなく、持ち時間（全体の長さ）がない。バーの割合が出せない。
- **仮定**: 待ちの種類ごとの持ち時間を画面の側で持つ（手番30秒・返し10秒・交換60秒、decisions §8）。持ち時間より長い残り（復帰で付け直したときなど）は満タンにする。
- **理由**: 秒数はいまのところ固定。server の秒数を変えるときは client の `src/lib/timer.ts` も合わせる必要がある（要望 R1）。

### B2. 時計のずれ
- **仮定**: `serverTime − 受け取った時刻` の直近5件のうち最大を使う（通信の遅れの分だけ小さく見積もられるため）。

## C. 交換

### C1. 交換の画面の形
- **場面**: §4.4 は「自分の手札」と「選ぶ1行・渡すボタン」だけを挙げているが、§7.6 は交換の待ちでも「待たれている人の枠」に残り時間を出すとしている。
- **仮定**: 対戦と同じ並び（上の帯・相手3人・場・メッセージ・自分・手札・ボタン）を使う。場は空のまま。何を何枚選ぶかの1行と「交換中…」はメッセージの欄に出す。
- **理由**: 相手の枠がないと §7.6 の残り時間が出せない。画面の形が交換と対戦で変わらないほうが疲れない。

### C2. 選び切ったあとの押し方
- **仮定**: 下位は候補以外のカードを暗くする。上位は手札全体が選べるので暗くしない。選べる枚数に達したあとに別のカードを押すと、いちばん前に選んだカードと入れ替える。
- **理由**: 選び切ったあとに全部が暗くなると、選び直せないように見えた（画像で確認）。

### C3. 受け取ったカードの目立たせ方
- **場面**: §4.4・§7.1 は受け取ったカードを「目立たせる」とだけ書いている。
- **仮定**: カードの枠を、外側に明るい金の輪がある専用の枠（ドットの段つき）にする。読み上げの名前に「受け取ったカード」を足す。対戦が始まってから、自分が最初に操作する（出す・パス・返す・スキップ）までの間と、上位が選んでいる間に付ける。
- **理由**: 最初はカードの上に金の矢印を付けたが、2段の手札では上の段に重なり、暗いカードの上では見えなかった（画像で確認）。選んだカード（上にずれて金の線）とは形で見分けられる。

## D. 対戦

### D1. 自分の番でないときの手札
- **design-client §7.13 に反映済み**
- **仮定**: 暗くしない（ふつうの明るさ）。押すとメッセージの欄に「いまは自分の番ではない」と出す。選択はできない。
- **理由**: 自分の番でないときに全部を暗くすると、ずっと暗い画面になって疲れる。

### D2. 自分の番でないときのボタンの場所
- **仮定**: ボタンは出さないが、場所（高さ）は空けておく。
- **理由**: 番が来るたびに手札の位置が上下に動かないようにするため。

### D3. 返しの一周で返せるカードがないとき
- **design-client §7.13 に反映済み**
- **場面**: §4.6「返せるカードを持っていない人には『スキップ』だけを出す（表示の形は同じにする）」。
- **仮定**: 「返す」と「スキップ」の2つのボタンを同じ形で出し、返せないときは「返す」を押せない状態にする。返せる手が1つだけ（スペードの3）のときは、カードを選ばなくても「返す」で送る。
- **理由**: 自分の画面の形だけの話で、ほかの人には伝わらない。形をそろえるほうが分かりやすい。

### D4. 形の2択と反則の確認の出し方
- **仮定**: 画面全体を覆う確認ではなく、ボタンの場所に出す（2択のボタン＋「やめる」、または確認の1行＋「やめる」「出す」）。カードを押し直したら閉じる。
- **理由**: 場と手札を見たまま決められる。重ねて半透明で覆う表示は使わない（ドット調の決まり）。

### D5. メッセージの欄の優先
- **仮定**: 交換中は「選ぶ1行」か「交換中…」、返しの一周では本人に「スペードの3で返しますか？」、ほかの人に「◯◯ が考えています」を、出来事のメッセージより優先して出す。それ以外は出来事・出せない理由・拒否の1行のうち最新のもの。
- **理由**: その場面でいちばん必要な1行だけを出すため。

### D6. メッセージを出さない出来事
- **design-client §7.13 に反映済み**
- **仮定**: `tempReverse` の解除（場が流れたときに起き、「場が流れた」と重なる）、返しの一周の開始・終了、スキップ、`dethrone`（同じ時点の `placed` で出す）、配る、交換の各手、ゲームと試合の終わり（画面が切り替わる）。`exchangeDone` は「交換が終わった」と出す。
- **理由**: §7.8 の表をコードに1つ持ち、情報を増やさない側に倒した。

### D7. 演出の細部
- **仮定**:
  - 革命の演出（画面が2コマ点滅し「革命」）は、革命が起きたときも戻ったときも出す。
  - 「たまったら（3つ以上）省く」は、再生中の1つも数に含める。1回の `state` で「出す・上がり・場が流れる」が同時に来た場合（8切りで上がるなど）は、演出をすべて省く。
  - 1回の `state` に複数のメッセージがあれば 0.6 秒ずつ切り替える。たまったら最後の2つだけにする。
  - 返し（`respond`）も「カードを出す」演出を使う。
- **理由**: §5.3・§7.8 の範囲で、短く・少なくする側に倒した。

### D8. 場のジョーカーの添え字
- **仮定**: カードの下に小さく出す。場が2段のときは、上の段の添え字をカードの上に出す（下の段に隠れるため）。
- **理由**: 画像で確認した。

### D8a. 縦に入りきらないとき
- **仮定**: 場はカードと札の高さより小さくしない。高さ 640px で「手札16枚（2段）」と「場に8枚以上（2段）」が重なるなど、縦に入りきらないときは、対戦の画面全体を縦にスクロールできるようにする（文字や絵は縮めない）。
- **理由**: §7.11 で縮小を禁じているため。画像では、640px で手札16枚、または場の2段のどちらか一方なら1画面に入ることを確かめた。

### D9. 強さが逆のときの場の枠
- **仮定**: 枠の線だけを赤にし、中の塗りはふつうの場と同じ暗い色にする。
- **理由**: 見本の赤い札の塗り（暗い赤）を場全体に使うと、面積が大きく重たく見えた。

### D10. 階級の札・順位の札
- **仮定**: 階級の札は見本どおり、大富豪だけ金、ほかは暗い札。上がった人は「2位」のような札（金。反則と都落ちは赤）に替える。自分が上がったときは自分の行に同じ札を出す。
- **理由**: 見本の色づかいに合わせた。

### D11. 送信中に押せなくするボタン
- **仮定**: 返事を待つ間は、その画面の操作ボタンをすべて押せなくする（押したボタンだけではない）。
- **理由**: 1つの待ちに対する操作はどれか1つしか通らないので、ほかのボタンを押せても意味がない。

## E. ロビー・結果・そのほかの画面

### E1. ロビーの押せる範囲
- **仮定**: ルール名・ON/OFF・「おすすめ設定に戻す」・ゲーム数・「コピー」は、押せる範囲を高さ 44px にし、隣どうしで重ねない（ルールの行の高さを 44px にした。見た目の札は見本の大きさ 28〜32px のまま、行の間が広がる）。「おすすめ設定に戻す」はルールの見出しの右に置き、見出しの行も 44px にする。「ゲームを始める」（ホスト以外は待ちの1行）と知らせの1行は下の帯に固定し、ロビーの欄が縦に入りきらないときは、その上の部分だけをスクロールする。
- **理由**: 44px 以上の決まりと、隣のボタンを押し間違えないこと（レビューの指摘で、上下に 12px 重なっていた作りをやめた）。実機の Chrome で、行の境目の上下1px を押すとそれぞれの行のボタンが反応し、押せる範囲どうしの重なりが0件であることを確かめた。高さ 800px では「ゲームを始める」まで1画面に入る。
- **その2で変わったこと**: ルールの枠にモードの切り替えの1行（44px と余白）が入ったため、大富豪モードのロビーも高さ 800px（幅 390px）ではゲーム数の枠の下の端が「ゲームを始める」の帯に隠れ、ロビーの欄を少しスクロールする必要がある（画像で確認。帯とボタンの位置・押せる範囲は変わらない）。カスタムでは、ルールの欄が長いので必ずスクロールする（H13）。

### E2. ホスト以外のロビー
- **仮定**: ON/OFF とゲーム数は、ボタンではなく同じ見た目の表示にする（押せない）。ルール名を押すと説明が出るのは、ホスト以外も同じ。

### E3. 名前の入力
- **仮定**: 「名前」の見出し・欄・1行（入れない理由か名前の誤り）・「参加する」だけを出す（ロゴは出さない）。最初の `state` が届くまでは「参加する」を押せない。入れない理由（満員・試合の途中）は、席のない `state` の席と段階から出し、そのときは「参加する」を押せない。
- **理由**: §4.2 の「出すもの」だけにした。

### E4. 前に参加したルームの名前
- **仮定**: 前に参加したルームでは、保存してある名前で `hello` を送る（名前がなければ「プレイヤー」）。サーバーは復帰のときは名前を使わない。

### E5. ゲームの結果の都落ちの知らせ
- **仮定**: 「都落ち！ ◯◯ は 大貧民へ」の「大貧民」は、その人の実際の順位の階級名にする（反則と重なれば「貧民へ」）。
- **理由**: §7.7 の「決め打ちしない」に合わせた。

### E5a. 無制限の試合を終えたとき
- **design-client §7.13 に反映済み**
- **場面**: §7.3 は「試合の結果の段階に出来事を通じて進んだときは、先にゲームの結果を見せる」としている。無制限の試合をホストが「試合を終える」で終えた場合も、出来事（`matchEnd`）を通じて進む。
- **仮定**: 先にゲームの結果を見せるのは、同じ `state` に `gameEnd` と `matchEnd` が入っているとき（最後のゲームが終わった瞬間）だけ。ゲームの結果の画面から「試合を終える」で進んだときは、試合の結果を直接見せる。
- **理由**: その場合、ゲームの結果はもう全員が見ている。同じ画面をもう一度出して「試合の結果へ」を押させるのは手間が増えるだけ（通しの確認で見つけた）。

### E6. 試合の結果の見出し
- **仮定**: 「総合」とする。総合順位・名前・合計点だけ。

### E7. メニュー
- **仮定**: メニューは項目の一覧（得点・この試合のルール・このゲームで出たカード・招待リンク・ルームを出る）で、押した項目だけを開く。得点の一覧では自分に「（あなた）」を付け、名前は切らずに全文を出す。出たカードは「誰が」「どのカード」を1行ずつ（マークは小さいドット絵、ジョーカーは「JK」）。
- **理由**: 1度に出す情報を減らすため。

### E8. 「ルームを出る」
- **仮定**: ホームへ戻るだけ（接続を閉じる）。通信の型に「抜ける」操作がないので、席は残り、server の決まり（切断から10秒で代役）に従う。

### E9. 開発用の見本ページと撮影用の引数
- **仮定**: `/dev/gallery`（固定のデータで各画面を描く）と、`?vw=&vh=`（画面の枠を指定の大きさに固定）は、開発のとき（`import.meta.env.DEV`）だけ有効。本番のビルドには含まれない。
- **理由**: ヘッドレス Chrome の画面は幅500px未満にできないため。

### E10. 一時的な知らせ（§7.13）
- **仮定**: 拒否の理由とホストの交代は、メッセージの行とは別の「知らせ」として4秒だけ出す。対戦では交換・返しの一周の案内より優先してメッセージの欄に出し、ロビーと結果の画面では下のボタンの上に1行で出す。接続・復帰の直後（eventsFull）と試合の切り替えでは、知らせ・メッセージの行・待ち行列を捨てる。
- **理由**: ロビーや結果の画面に、対戦の出来事のメッセージを持ち込まないため。

## F. 接続

### F1. 接続直後の ping
- **仮定**: つながったらすぐ `"ping"` を1回送る（名前の入力中で `hello` をまだ送らないときも）。
- **理由**: server-assumptions C4（一度も送信していない接続はサーバーから閉じきれない）。

### F2. 閉じられたコードの扱い
- **仮定**: 4001（別の画面で開かれた）・4003（ルームが閉じた）・4002（入れない）はつなぎ直さない。4000（応答なし）・4004（接続が多すぎる）・それ以外はつなぎ直す。
- **理由**: 4004 は一時的なもの（ほかの接続が閉じれば入れる）と考えた。

### F3. ルーム ID の形
- **仮定**: URL のルーム ID が 22 文字の英数字と `-` `_` でなければ、つながずに「ルームが見つからないか、つながりません」を出す。

### F4. つながる前の無応答とStrictMode
- **仮定**: 15秒の無応答の期限は、WebSocket を作った時点から数える。つながらないまま過ぎたら接続を捨て、一度もつながらない失敗として数える（3回であきらめる）。通信の部分は「開始 → 後始末 → 開始」で作り直せる作りにし、開発では React の StrictMode を有効にしている（実機で、最初の接続はつながる前に閉じられて何も送らず、hello は1回、操作は待ちごとに1回だけ送られることを確かめた）。

## G. engine・server・設計書への要望（変更はしていない）

- **R1**: `DeadlineView` に持ち時間（全体の長さ）を足してほしい。いまは client が秒数を二重に持っている（B1）。
- **R2**: 通信の型に「ルームを抜ける」操作がない（E8）。ロビーで間違えて入った人が席を空けられない（server-assumptions A4 のとおり）。
- **R3**: design-client §7.4 の「8枚以下なら1段」と見本（12枚が1列）が違う。§7 を優先して2段にした。

## H. その2（カスタムモード）

### H1. モードの切り替えの場所
- **場面**: design-2 §4.1 は「ルールの枠のいちばん上に、モードの切り替えを置く」としている。枠の中には見出し「ルール」と「おすすめ設定に戻す」の行がある。
- **仮定**: 見出しの行（「ルール」と右のボタン）のすぐ下に置く。形はゲーム数の3つのボタンと同じ札を2つ並べたもの（2列）。大富豪モードの画面も、この1行の分だけ縦に伸びる。ホスト以外には同じ見た目で押せない表示。いま選ばれているモードを押しても何も送らない。
- **理由**: 見出しは枠の名前なので、その上に置くと何の切り替えか分かりにくい。

### H2. カスタムの見出し「定番」「応用」
- **仮定**: 「定番」「応用」は、ルール名と同じ 16px で、色は暗い文字（`--muted`）にする。行の高さは 28px。
- **理由**: ルールの行（ON/OFF）と見分けがつき、目立ちすぎないため。

### H3. 4止めを押せない形
- **場面**: §4.1「8切りが OFF の間は押せない形（暗くする）で出す」。OFF の行は、その1からすでに暗い文字（`--muted`）。
- **仮定**: 前提のルールが OFF の行は、OFF の行よりさらに暗い色（既存の `--dim-line`）にし、ON/OFF のボタンを押せなくする。ルール名を押すと説明が出るのは同じ。前提の判定は engine の `RULE_MODULES[].requires` を使う（4止めだけに決め打ちしない）。8切りを OFF にしたときは、client は4止めを外さずに送り、サーバーが直した結果（4止めも OFF）が届く。

### H4. 「ダイヤの3スタート」の表示名
- **場面**: ロビーの2列では、幅 360〜430px のどれでも「ダイヤの3スタート」が1行に入らず、ON/OFF の札に重なった（画像で確認）。
- **仮定**: ロビーだけ「ダイヤの3」「スタート」の2行に分けて出す（行の高さ 20px × 2 = 40px で、44px の行の中に収まる）。名前は縮めない・変えない。読み上げの名前は1つの「ダイヤの3スタート」。ほかの画面（メニューのルール一覧、説明）は1行のまま。
- **理由**: 文字を縮めることは §7.11 で禁じている。表示名は decisions §6.0 の表のとおりにする。

### H5. 説明文（8種）
- **仮定**: `rules-text.ts` に次の8つを足した（自分たちの言葉で書いた）。
  - 4止め「8切りが起きたとき、4を2枚出すと8切りを止められる。止めたあとも8は場に残る。」
  - 激縛り「同じマークで数字が1つ上のカードが続くと、場が流れるまで同じマークで次の数字しか出せない。」
  - ダイヤの3スタート「ダイヤの3を持つ人から始める。最初の1手には、ダイヤの3を必ず入れる。」
  - 砂嵐「3を3枚そろえて出すと、場に何が出ていても勝ち、すぐに場が流れる。」
  - 7渡し「7を出したら、出した枚数まで手札を次の人に渡せる。渡さなくてもよい。」
  - 10捨て「10を出したら、出した枚数まで手札を捨てられる。捨てなくてもよい。」
  - 9リバース「9を出すと、場が流れるまで順番の回る向きが逆になる。」
  - K スキップ「K を出すと、出した枚数の人数だけ順番を飛ばす。」

### H6. 7渡し・10捨ての選択
- **仮定**:
  - 選ぶ人の手札は、どのカードも暗くしない。上限まで選んだあとに別のカードを押すと、いちばん前に選んだカードと入れ替える（交換の C2 と同じ）。
  - ボタンは左「渡さない」（「捨てない」）、右「◯枚を渡す」（「◯枚を捨てる」）。0枚のときの右のボタンは「渡す」（「捨てる」）と出して押せない（「出す」のボタンと同じ扱い）。
  - 選んでいる間も「あなたの番」と残り時間のバーを出す（選ぶのは自分への待ちのため）。
  - 7渡しの相手の枠の明るい枠は、選んでいる本人の画面にだけ出す（ほかの人には「◯◯ が選んでいます」だけ）。読み上げでは相手の枠に「渡す相手」と付ける。
- **理由**: 情報を増やさない側に倒した。相手が誰かは、渡したあとのメッセージで全員に分かる。

### H7. 4止め・スペ3返しの最初の選択
- **仮定**: 返せる組み合わせが1つだけのときは、待ちが変わった時点で、その組み合わせのカードを選んだ状態から始める（スペ3返しも同じ。design-2 §4.3）。選んだカードを押して外しても、その1と同じく「返す」はその1つの組み合わせで送れる。4止めの返しで暗いカードを押したときの理由は、縛りではなく「場のカードより弱いか、枚数・種類が合わない」にする（4止めは縛りを無視するため）。

### H8. 札（激縛り・逆回り）
- **仮定**: 「激縛り」は「縛り」と同じ札（明るい文字・ふつうの枠）にマークのドット絵を添える。「逆回り」も同じ札。赤い札は「強さが逆」（革命中・J バック中）だけに使う。札が多いときは、その1と同じく折り返す（5つで2行。画像で確認）。並びは 革命中・J バック中・縛り・激縛り・逆回り。

### H9. ダイヤの3の案内と出せない理由
- **仮定**: 最初の親の手番で、義務があるあいだ（`openingCard` が null でない）、メッセージの欄に「最初の1手には ダイヤの3を含めます」を出す。ただし、暗いカードを押して出せない理由を出した直後は、その理由を残す。理由の判定の順は「選んだカードと組み合わせられない」→「最初の1手にはダイヤの3が必要」→「激縛りの続きに合わない」→「縛りのマークに合わない」→「弱いか、枚数・種類が合わない」。激縛り中は、出せないカードの理由をすべて「激縛りの続きに合わない」にする（激縛り中に出せる手は、激縛りの続きと砂嵐だけのため）。

### H10. メッセージの言い回し
- **仮定**:
  - 7渡しで自分が渡したとき：「あなた が △△ に 渡した」（設計書の「あなたが」に、その1の「あなた が 10を1枚 出した」と同じ空白を入れた）。
  - K スキップで2人以上を飛ばしたとき：名前を「・」でつなぐ（「K スキップ！ ゆい・CPU 4 を飛ばした」）。
  - 9リバースの解除、選択の始まり（`choiceStart`）、選ばなかったとき（`choiceSkip`）はメッセージなし。
  - 4止めの成立は、返し（`respond`）の出来事の `toDiscard` で見分けて「4止め！」にする（スペ3返しは、その1と同じ「スペ3返し！」）。
  - 4止めの返しを聞かれている人：「4を2枚出して 8切りを止めますか？」。ほかの人：その1と同じ「◯◯ が考えています」。

### H11. 7渡しで受け取ったカードの強調の消し方（design-2 §6.3）
- **仮定**: 「自分が送った操作が受理された」は、届いた `state` の `acceptedReqId` が、送ってまだ結果の分からない操作（`action`）の `reqId` のどれかと同じかで判定する。結果の分からない操作の `reqId` は複数覚える（送信待ちが3秒で解けて同じ操作を送り直したあとに、最初の操作の受理が届く場合があるため）。覚えは、受理（その `reqId`）・拒否（その `reqId` の `error`）・接続の終了・試合の識別子の変化で片付ける。`acceptedReqId` は、engine がその操作を受け付けた入力の処理でサーバーが本人に送る `state` にだけ付く（protocol.ts、server-assumptions G9）。設定・開始・次のゲームなどのホストの操作には付かないので数えない。拒否（`error`）、時間切れの自動の操作や他人の操作で進んだ `state`（送信待ちの間に届いたものも含む）では消さない。送信待ちが3秒で解けたあとに届いた受理の `state` では消す。
- **理由**: 前は「送信待ちの間に `state` が届いた」を受理の証拠にしていたため、「強調中に操作を送る → 先に処理された時間切れの `state` が届く → 自分の操作は `staleAwait` で拒否」の順で、拒否されたのに強調が消えていた（実装レビューの指摘）。届く順だけでは見分けられないので、サーバーに最小の印（任意の1項目）を足した。
- **補足**（実装レビューの指摘）: 前は最後に送った操作の `reqId` だけを覚えていたため、「強調中に操作 A を送る → 3秒で送信待ちが解け、同じ操作を B として送り直す → A の受理が届く → B は `staleAwait` で拒否」の順で、受理されたのに強調が消えなかった。

### H12. 出たカードの履歴
- **仮定**: 10捨てで捨てたカードは、捨てた人の行に、カードのあとに「10捨て」と暗い文字で添える。4止めで返した4は、その1の返しと同じく1行（印なし）。メニューの「この試合のルール」は、16種が入りきらないときに縦にスクロールする（その1の8種では変わらない）。

### H13. 確かめた画像と、古くなったその1の画像
- `docs/mock/client/custom-*.png`（見本ページ `/dev/gallery` をヘッドレスの Chrome で撮ったもの）。カスタムのロビーは、ルールの欄を全部見せるために高さ 1240px でも撮った（`custom-lobby-w360/390/430.png`。実際の高さでは、ロビーの欄が縦にスクロールする。`custom-lobby-h800.png`）。

## I. その3（超富豪モード）

### I1. ロビー
- **仮定**: モードの切り替えは3つのボタン（大富豪・カスタム・超富豪）を同じ幅で1行に並べる（その2の2列を3列にした。大富豪・カスタムのときもボタンの幅が変わる）。超富豪では「定番」「応用」の見出しで16種を並べ、ホストにも ON/OFF を押せない形（ホスト以外と同じ札）で見せる。「前の大富豪が 特権を使える」の1行は、モードの切り替えの下、ルールの一覧の上に明るい文字で出す。超富豪から大富豪・カスタムへ切り替えると、16種を送ったものとしてサーバーが直す（大富豪なら定番8種がすべて ON、カスタムなら16種すべて ON）。

### I2. 特権の選択の画面
- **仮定**:
  - 6種の行は、選んでいる行を明るい枠（`f hot`、名前も明るい文字）、選んでいない行を暗い枠（`f dim`）にする。枠がいっぱいのときの選んでいない行は、押せない形（文字も暗く）にする。
  - 選ぶ人の自分の行には、ほかの待ちと同じく「あなたの番」と残り時間のバーを出す（7渡しの選択と同じ、H6）。
  - 「特権 2」の札は、選んでいる間も出す（残りの個数 = 枠の数。全員に見える数）。
  - 選ぶ人の手札は暗くせず、押しても何も起きない。
  - 送信中（途中の保存・決定）は、行と「決定」をすべて押せなくする（その1の送信中の扱い。どのボタンの送信かは区別しない）。
  - 選ぶ人の画面では、「決定」を画面の下に固定し、その上（上の帯・相手の枠・特権の一覧・メッセージ・自分の行・手札）を縦にスクロールさせる（ロビーの「ゲームを始める」と同じ作り）。高さ 800px・手札2段で「決定」の下半分が画面の外に出ていたため（実装レビューの指摘）。中身が画面より短い背の高い窓では、手札と「決定」の間が空く（ボタンは下に付いたまま）。ほかの人の画面（選んでいるのを待つ側）と、対戦・交換の画面は、包みの要素を `display: contents` にして配置を変えない（見本ページの同じ場面を前後で撮り、画像が1バイトも変わらないことを確かめた）。

### I3. 特権のボタンの並び
- **仮定**: メッセージの欄のすぐ下に、ボタンの数で等分した1行（最大3つ。枠は最大3個のため）で並べる。高さ 44px。ふだんは既存の `btn2`（金の線の枠）、開いている特権は明るい枠（`f hot`、明るい文字）。スキップの ON は金の塗り（`f btn`、「N枚を出す」と同じ枠）にし、表記を「スキップON」にする（提案をユーザーが承認して直した（2026-11-17）。明るい枠だけでは ON/OFF の見分けが弱かったため。`.btn` の高さ 52px・`letter-spacing` 2px・`padding` 0 8px は `.bar .barBtn`・`.bar .skipOn` で 44px・0・0 4px に戻し、幅 360px・ボタン3つでも切れない）。使えないもの（場が空の強制流し、相手のいない透視・強奪）は既存の押せないボタンの形（暗い枠）。ボタンをもう一度押すと選択の枠を閉じる。別の特権を押すと切り替わる。
- **理由**: 並びを出さないときは場所も取らない（大富豪・カスタムの画面は変わらない）。

### I4. 選択の枠
- **仮定**:
  - 場の枠と同じ位置・余白に、場の代わりに出す（開いている間は場のカードと札は見えない）。
  - 透視・強奪：相手の名前のボタンを縦に並べ、いちばん下に「やめる」。名前は枠の幅で切る。強奪の問いかけは読点のあとで改行する。強奪はカードを選ぶまで名前のボタンを押せない。
  - 独裁：13個の数字のボタンを7列×2行（3〜9 / 10〜2）、その下に「やめる」。指定できない数字は押せない形。
  - 革命・強制流し：問いかけと「やめる」「使う」（左右）。
  - 使ったあとは待ちの番号が変わるので、枠・強奪のカード・スキップの ON は自然に閉じる（design-3 §6.1）。拒否されたときは開いたまま。

### I5. スキップ
- **仮定**: スキップを付けられないときの判定は、形の2択や反則の確認のあと、実際に送る手で行う（組か階段かで `canSkip` が変わりうるため）。付けられないときは「この手には スキップを付けられません」を出し、形の2択・反則の確認を閉じる（スキップの ON はそのまま）。

### I6. 札と透視の表示
- **仮定**:
  - 相手の「特権 2」の札は、階級の札と横に並べると幅 360px で入らないため、枚数の下に1行足して出す（持ち主の枠だけ高くなり、同じ行の3つの枠は同じ高さにそろう）。自分のときは、自分の行の階級の札の右に出す。
  - 相手の「パス」の札は、枠の上の辺から 24px 上に持ち上げる（`top: -24px`。提案をユーザーが承認して直した（2026-11-17）。幅 360px で枠の上の行の中央の階級の札に重なって読めなかったため。札の高さは 28px、ヘッダーの文字の下端とは 4px 空く）。
  - 「独裁 7」は「縛り」と同じ札（明るい文字・ふつうの枠）。札の並びの最後。
  - 透視で見たカードは、対象の枠の中、枚数（と特権の札）の下に、カード単位で折り返して出す。赤いマーク（♥♦）とジョーカーは赤い文字、♠♣はふつうの文字。枠の外の下には出さない（場の手を出した人の印 ▼ と重なるため）。
  - 見られたカードの赤い線は、カードの枠の上の辺に重ねる（2段の手札では、下の段のカードの線が上の段のカードの下端に重なって見える）。

### I7. メッセージ
- **仮定**:
  - 透視の持ち主には「あなた が △△ に 透視を使った」（ほかの人と同じ言い方）。強奪の持ち主・対象には、設計書のとおり中身の1行だけ（「◯◯ が △△ に 強奪を使った」は出さない）。
  - 革命の特権は、続く `revolution` の出来事で「革命！」を出す（特権の出来事では出さない。演出もその1と同じ）。
  - 強制流しは「強制流し！」の1行だけ（続く場の流れの「場が流れた」は出さない）。
  - スキップは、続く `skipped` と合わせて「スキップ！ △△ を飛ばした」の1行。K スキップと重なったときも、この言い方で飛ばした全員を出す。飛ばされた人がいないときは「スキップ！」。
  - 7渡し・10捨てにスキップを付けたときは、選択をはさむので `skipped` が別の `state` で届く。そのときは、出した `state` で「スキップ！」、選択が終わった `state` で「スキップ！ △△ を飛ばした」と出す（「K スキップ！」にしない）。「飛ばす席が決まるのを待っている」ことは、出来事の記録（`Feed.skip`）にゲームの番号と出した席で覚え、試合が変わると捨てる（記録は試合ごと）。出した席の `skipped` で使い終え、手番が進んだ（`play`・`pass`・`respond`）・場が流れた・ゲームが変わったときにも捨てる（飛ばす人がいなかったスキップの覚え書きが、あとの K スキップに付かないように）。返しの一周のスキップ（`respondSkip`）では捨てない（一周が不成立なら残りの効果としてスキップが続くため）。返しが成立した `respond`（4止めを含む）では捨てる（engine は成立したときに残りの効果を捨てるので、`skipped` は来ない）。復帰した直後（`eventsFull`）も、届いた全件から覚え書きを作り直す。
  - 特権の選択の開始はメッセージなし（選択の画面の案内で分かる）。
  - 札の文字・1枚の短い表記（♠K、♥10、ジョーカー）。強奪のメッセージにも同じ表記を使う。
  - 拒否の文言：`invalidAbility`「その特権は使えない」、`abilityNotUsable`「いまは その特権を使えない」、`cannotSkip`「この手には スキップを付けられません」。
  - 12文字の名前の「◯◯ が 特権を選んでいます（2個）」は、メッセージの欄の幅で切れる（その1と同じく1行で切る）。

### I8. 出せない理由
- **仮定**: 暗いカードを押したときの理由の判定の順は「選んだカードと組み合わせられない」→「最初の1手にはダイヤの3が必要」→「独裁で封じられている」（そのカードの数字が封じた数字のとき。返しの一周でも同じ）→「激縛りの続きに合わない」→「縛りのマークに合わない」→「弱いか、枚数・種類が合わない」。

### I9. 残り時間のバー
- **仮定**: 特権の選択のバーの基準は 60秒（`FULL_MS.abilitySelect`）。特権を使って期限を引き継いだ手番のバーは、引き継いだ残りで出す（30秒の基準のまま）。

### I10. 確かめた画像
- `docs/mock/client/chofugo-*.png`（見本ページ `/dev/gallery` をヘッドレスの Chrome で撮り、枠の幅に切り出したもの）。
- 特権の選択（選ぶ人）は「決定」を下に固定したあとで撮り直した：`chofugo-select-w{360,390,430}-h{640,800}.png`（スクロールしていない状態）、`chofugo-select-w{360,390,430}-h640-scrolled.png`（いちばん下までスクロール）、`chofugo-select-full-w390-h800.png`（枠がいっぱい・手札12枚）、`chofugo-select-w390-full.png`（高さ 1240px で全体）。どの組み合わせでも「決定」の下端が画面の中にあることを、要素の位置（`getBoundingClientRect`）で確かめた。前の `chofugo-select-w390.png`・`chofugo-select-w430.png`・`chofugo-select-full.png` は消した。ほかの人の画面（`chofugo-select-other-*`）は変わらないので撮り直していない。

### I11. 強奪の枠と、ふつうの選択
- **仮定**: 強奪の枠を開くときと閉じるときに、ふつうの手の選択（出す手のカード）を空にする（design-3 §6.3）。ほかの特権の枠では、ふつうの選択は残す（場の枠の位置が変わるだけで、手札の選び方は変わらないため）。

### I12. 確かめ方
- 高さ 640px・手札16枚の特権の選択で、「決定」が下に固定されて見えていること、縦にスクロールして手札の下の段に届くこと、強奪の枠（360×640）で手札と名前のボタンの両方に届くことを、ヘッドレス Chrome（CDP）でスクロールして確かめた（`chofugo-select-w360-h640-scrolled.png`、`chofugo-panel-steal-w360-h640-scrolled.png`）。
- 実際の画面（開発サーバー、幅 500px の窓・アプリの枠は 430px）で、受け身のボット3席を相手に、ヘッドレス Chrome の席を CDP で操作し、特権の選択（途中の保存・2個の選択・決定）と6種の使用（透視・強奪・独裁・革命・強制流し・スキップ）を画面のボタンから行った。

## J. 第2段階（特殊ルール8種、design-4 §4・§6）

### J1. ロビー
- **仮定**: 見出し「特殊」は「定番」「応用」と同じ形（H2）にし、8種を §4.1 の並びで同じ2列に並べる（`rules-text.ts` の `SPECIAL_RULE_ORDER`）。6戻しが押せない形になるのは、4止めと同じく engine の `RULE_MODULES[].requires`（`['temp_reverse_on_j']`）を見る既存の仕組みのまま（コードは変えていない。テストと `stage2-lobby-6locked.png` で確かめた）。「全部 ON」は `CUSTOM_MODE_RULE_IDS`（24種）を送る既存のボタンのまま。超富豪は24種を「定番」「応用」「特殊」の見出しで並べる。
- 幅 360px でも8種の表示名（「Q ボンバー」「銀河鉄道」を含む）は1行に入る（H4 のような2行の分け方は要らなかった）。

### J2. 選択の種類の決め方
- **仮定**: `MyAwaiting.rule` から、engine の `RULE_MODULES[].choiceKind`（give・discard・salvage・trade・call）で決める（`choice.ts` の `choiceKindOf`）。client にルール ID ごとの表を別に持たない。

### J3. 銀河鉄道の選択
- **仮定**: 10捨てと同じ作り（どのカードも上限まで選べ、上限を超えるといちばん前に選んだカードと入れ替える）。ボタンは左「交換しない」、右「◯枚を交換」。0枚のときの右のボタンは「交換」と出して押せない（H6 の「渡す」「捨てる」と同じ扱い）。

### J4. 銀河鉄道のメッセージの文言
- **場面**: 設計の「捨て札と交換するカードを2枚まで選べます」は、幅 360px のメッセージの欄（1行で切る作り、E10・I7）に入らず、「選べま」で切れた（画像で確認）。
- **仮定**: 「捨て札と」を省き、「交換するカードを2枚まで選べます」にした（すべての幅で同じ文言）。文字は縮めていない。
- **理由**: メッセージの欄を2行にすると既存の配置が変わる。何と交換するかは、場の9の3枚組と、交換のあとのメッセージ「銀河鉄道！ …」で分かる。設計の文言に戻す場合は、幅 360px で別の言い方が要る（ユーザーの判断待ち）。

### J5. 闇市の選択
- **仮定**:
  - 場の枠の位置に、強奪の枠と同じ枠（`f win` と同じ余白・大きさ）を出す。見出し「闇市：相手を選ぶ」、その下に `targets` の相手のボタンを縦に並べる（名前は枠の幅で切り、右に残り枚数「6枚」を必ず見せる）。
  - 相手のボタンは押すと選び、もう一度押すと外す。選んでいないボタンは金の線の枠（`btn2`）、選んでいるボタンは特権のボタンの開いている形（`f hot hi`）。強奪の枠と違い、押してもすぐには送らない（カードと同時に送るため）ので、金の塗り（`btn`）は使わない。
  - 枠の中に「やめる」は置かない。「使わない」「◯枚を交換」は、ほかの選択と同じく画面の下のボタンの欄に出す。
  - 相手を選ぶ前も、手札のカードは上限（`max` = min(2, 自分の手札)）まで選べる。相手を選ぶと、ちょうどの枚数（min(上限, 相手の残り枚数)）が上限になり、多すぎる分は前に選んだものから外す（「あとから選んだカードを残す」）。相手を外しても選んだカードはそのまま。
  - メッセージの欄：相手を選ぶ前は案内を出さない（直前のメッセージのまま。枠の見出しで分かる）。相手を選んだあとは「渡すカードを◯枚選んでください」。
  - 右のボタンの表記は、ほかの選択と同じく選んでいる枚数（「2枚を交換」。0枚は「交換」）。相手を選び、ちょうどの枚数を選んだときだけ押せる。送る内容は `cards` と `target`。「使わない」は `cards: []` だけ（`target` は付けない）。
  - 相手・数字の選択は、手札の選択と同じく試合・ゲーム・待ちの番号に結び付ける（変わったら捨てる）。

### J6. Q ボンバーの選択
- **仮定**:
  - 場の枠の位置に、独裁の枠と同じ枠を出す。見出し「Q ボンバー：数字を◯個まで宣言」、3〜9 / 10〜2 を独裁と同じ7列×2行で並べ、「JOKER」はその下に1行（独裁の「やめる」の行と同じ幅いっぱいのボタン）で出す。
  - **JOKER を数字と同じ升に入れない理由**: 幅 360px で7列の升の内側は約28px（枠の 6px を引いた分）で、「JOKER」（約40px）が入らない。文字を縮めない・略さないため、1行に分けた。
  - 選んでいないボタンは `btn2`、選んでいるボタンは `f hot hi`（J5 と同じ）。上限を超えて押すと、いちばん前に選んだものと入れ替える。
  - メッセージの欄には案内を出さない（直前のメッセージのまま。見出しで分かる）。手札は暗くせず、押しても何も起きない（手札0枚でも同じ画面）。
  - ボタンは左「宣言しない」、右「宣言する」（1個以上で押せる）。送る内容は `cards: []` と `ranks`。「宣言しない」は `cards: []` だけ。

### J7. メッセージ
- **仮定**:
  - 闇市の当事者には「△△ と 2枚 交換した」だけ（「闇市！」を付けない。7渡しの当事者の言い方と同じ扱い）。△△ は相手（使った側なら選んだ相手、相手の側なら使った人）。
  - オーメンは、`revolution` の出来事に `rule: 'triple6_revolution'` が付いているとき、その行の前に「オーメン！」を足す（`eventLines`）。革命が戻るときは「オーメン！」「革命が戻った」。
  - 6戻しは、`tempReverse` の解除（`active: false`）に `rule: 'cancel_reverse_on_6'` が付いているときだけ「6戻し！ J バック解除」。場が流れたときの解除は今までどおり出さない。
  - 大革命：出来事は `play → revolution → instantWin → placed → fieldCleared`（engine-assumptions H3）なので、そのままだと最後に「場が流れた」が残り、「◯◯ が 1位で 上がった」とも重なる。同じ state で大革命を出した人の `placed`（`finish`）のメッセージと、理由 `quad2_instant_win` の `fieldCleared` のメッセージは出さず、「大革命！ ◯◯ が上がった」を残す。革命の行（「革命！」）は出す。都落ちが続くときは「都落ち！ ◯◯ は 4位」が最後に残る。
  - DEATH の「◯人」は `discards` の数（捨てた人の数）。Q ボンバーの数字の並びは届いた `ranks` の順（engine が 3〜2・JOKER の順に並べる、engine-assumptions H4）。誰も持っていなかった宣言でも「Q ボンバー！ 7」と出す。
  - 12文字の名前の闇市のメッセージは、その1と同じく欄の幅で切れる（`stage2-play-msg-trade-12-w360.png`）。

### J8. 演出
- **場面**: 大革命は1回の state で「出す・革命・順位の確定・場が流れる」の4つの演出になり、待ち行列の決まり（3つ以上で残りを省く、design-client §5.3）で、革命の演出も出なくなる。
- **仮定**: 待ち行列の決まりは変えず、大革命を出した人の順位の確定（`finish`）と、理由 `quad2_instant_win` の場が流れる演出を省く（`animsFor`）。演出は「出す → 革命」の2つになる。都落ちの順位の確定（赤）は省かないので、都落ちが起きたときは3つになって全部省かれる（既存の決まりのまま）。オーメンは「出す → 革命」の2つで、何も変えていない。

### J9. 出たカードの履歴
- **仮定**: 効果で動いたカードは、元の持ち主の行に、カードのあとにルール名を暗い文字で添える（10捨ての「10捨て」と同じ形。H12）。DEATH・Q ボンバーは1つの出来事から席ごとに1行。闇市は当事者にだけ、使った人の行に渡したカード、相手の行に相手が渡したカード（使った人が受け取ったカード）を出す。大革命で残りの手札がなかったとき（最後の4枚で出した）は行を足さない。行の key は `seq:seat`（1つの出来事の行どうしは席が違う）。

### J10. 状態の札
- **仮定**: 「色縛り 赤」「色縛り 黒」は「縛り」と同じ札（明るい文字・ふつうの枠）で、「赤」だけ赤い文字（`redt`）。並びは 革命中・J バック中・縛り・激縛り・色縛り・逆回り・独裁。札が6つでも幅 360px で2行に折り返して収まる（`stage2-play-badges6-w*-h640.png`）。

### J11. 出せない理由
- **仮定**: 判定の順は I8 の「縛りのマークに合わない」のあとに「色縛りの色に合わない」を足した（engine も、理由が重なるときは第1段階の理由を先に返す。engine-assumptions H10）。手番のときだけで、返しの一周（スペ3返し・4止めは色縛りを無視する）とジョーカーでは理由にしない。

### J12. 受け取ったカードの強調
- **仮定**: 7渡しと同じ `nextGift` に、銀河鉄道で自分が引いたカード（`salvage.took`）と、闇市で自分が受け取ったカード（使った側は `taken`、相手の側は `given`）を足した。使った本人には、自分の `choose` が受理された state で出来事が届くが、「消す → 足す」の順なので強調は残り、次の自分の操作で消える（テストで確かめた）。

### J14. bots.mjs
- `--rules all` はカスタムで24種（`ALL_RULES` に8つ足した。engine を読み込まないので写し）。闇市は3分の1で使わず、使うときはでたらめな相手と、ちょうど min(上限, 相手の手札) 枚（`view.game.handCounts` を見る）。Q ボンバーは 0〜上限個の別々の数字（0個なら `ranks` を付けない）。銀河鉄道は 7渡し・10捨てと同じ（0〜上限枚）。`--passive` ではどれも選ばない。出来事の数え上げに `colorLock`・`purge`・`salvage`・`trade`・`callDiscard`・`instantWin`・`revolution:triple6_revolution`・`tempReverse:cancel_reverse_on_6`・`fieldCleared:quad2_instant_win` を足した。
- 実装の時点で確かめたのは構文（`node --check`）と、選び方の関数を取り出して乱数で300回ずつ回した結果（闇市の枚数がちょうど・Q ボンバーの重複なし）。サーバーを通した通しは J15 で確かめた。

### J15. 動かして確かめたこと（2026-11-18、設計担当）
- **ボットの通し（開発サーバー）**：カスタム24種・超富豪（ボット4席）、超富豪（ボット1席＋CPU 3席）を各5ゲーム完走、拒否0件。カスタム24種を10ゲーム動かした回では、Q ボンバー17回・5色縛り22回・6戻し7回が起きた。本物の3枚組・4枚組の役（オーメン・DEATH・銀河鉄道・闇市・大革命）は、でたらめに出すボットでは起きにくいので、下のとおり種を固定して確かめた。
- **Chrome の1席（390×740 の枠、種を固定したルーム＋受け身のボット3席）**：
  - ロビー：カスタム →「全部 ON」で24種。J バックを OFF にすると6戻しが OFF になって押せなくなり、「全部 ON」で戻る。
  - Q ボンバー：3 → 7 → K と押すと、上限2個で 7・K が残る。宣言すると、全員の手札からその数字が捨てられる。
  - 銀河鉄道：2枚を置いて、捨て札から2枚を受け取る。受け取ったカードが手札の中で目立つ。
  - 闇市：相手を選び、2枚を渡して、相手のいちばん強い2枚を受け取る。履歴に、当事者として渡したカードと受け取ったカードが出る。選ばずに15秒たつと「使わない」になって進む。
  - DEATH：相手3人の枚数が1枚ずつ減り、「DEATH！ 3人が1枚ずつ捨てた」と出る。
  - オーメン：革命の演出のあと「オーメン！」→「革命！」と出る。
  - 大革命：「革命！」→「大革命！ あなた が上がった」と出て1位になり、場が流れて次の人が親になって続く。
- **メッセージの出方について**：メッセージは 600ms ごとに1行ずつ出し、たまりすぎると最後の2行だけにする（その1からの作り）。ボットを 300ms 間隔で動かすと、「DEATH！」「オーメン！」の行は飛ばされて出ない。CPU（約1秒）や人の速さでは出る（ボットを 1.5 秒間隔にして確かめた）。
- **本番用のビルド（`vite preview`、テスト用の機能なし）**：種の指定は 400、テスト用の経路は 404、別のサイトの Origin は 403。大富豪・カスタム24種・超富豪（ボット4席）と超富豪（ボット1席＋CPU 3席）を各5ゲーム完走、拒否0件。
