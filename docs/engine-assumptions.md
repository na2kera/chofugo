# engine 実装時に置いた仮定

> `packages/engine`（その1）を実装する中で、`decisions.md`・`design.md`・`spec_v0.1.md` に答えがなかった場面、または解釈に迷った場面の記録。
> 各項目は「場面 / 置いた仮定 / 理由」の順に書く。遊んでみて、あるいはレビューで見直してよい。

## A. 公開関数・状態の形

### A1. `createMatch` の戻り値
- **場面**: design §3.2 では `createMatch` が `{ state, events }` を返す。一方で、未実装のルールや不正な設定はエラーにする必要がある。
- **仮定**: `{ ok: true; state; events } | { ok: false; error: ConfigError }` を返す。エラーにするのは、知らないルール ID、重複、未実装（その2の8種）、前提ルールの不足、ゲーム数の誤り、種の誤り、形の誤り。
- **理由**: engine は例外を投げない（design §3.1）ので、エラーは値で返すしかない。`applyAction` と同じ形にそろえた。

### A2. `MatchConfig` の中身
- **場面**: design §3.4 では config に「有効なルール、ゲーム数、閾値」を持つとある。§8.1 では `matchId` をサーバーが渡すとある。
- **仮定**: `MatchConfig = { matchId, rules, gameCount }` とした（`gameCount` は `5 | 10 | null`、null は無制限）。特権枠の閾値はその3で足す。`matchId` は `MatchState.matchId` にも写す。
- **理由**: その1では閾値を使わない。後から項目を足しても既存の項目は変わらない。

### A3. 種と乱数
- **場面**: design §8.1 では、乱数の状態を「32ビット整数4個」に固定し、方式名を明記することになっている。
- **仮定**: 方式は xoshiro128\*\*。種 `Seed` は 32ビット符号なし整数4個で、全部0は不可とした。xoshiro128\*\* の最初の出力は状態の一部だけで決まるので、種から状態を作るときに16回空回しする。
- **理由**: 小さな種（`[1,2,3,4]` など）でも、最初の乱数が偏らないようにするため。

### A4. 配り方の乱数の使い方
- **場面**: §2.2 では「14枚になる2人は毎ゲームランダム」とだけ決まっている。
- **仮定**: 山札をシャッフルし、別に席の並びもシャッフルする。席の並びの先頭2人を14枚にし、席0から順に山札を切り分ける。1ゲーム目の最初の人は、そのあとに乱数で決める。
- **理由**: 再現できて、偏りのない方法なら何でもよいため。

### A5. 回数つき試合の最終ゲームと `endMatch`
- **decisions §14.14 に反映済み**
- **場面**: design §3.3 には「`endMatch` は無制限の試合を終える」とある。§14.12 には「ゲームの結果画面のときだけ終えられる」とある。回数つき試合の最終ゲームのあとのフェーズは決まっていない。
- **仮定**: 回数つきの試合では、最終ゲームが終わると `gameEnd` と `matchEnd` を続けて出し、そのまま `matchResult` に移る（`gameResult` を経ない）。`endMatch` は、無制限の試合の `gameResult` フェーズでだけ受け付ける。回数つきの試合で送られたら `notUnlimited`、それ以外のフェーズで送られたら `wrongPhase` を返す。
- **理由**: 最終ゲームの結果は `results` と `game` に残るので、画面ではゲームの結果と試合の結果を両方出せる。回数つきの試合を途中で終える要件はない。

### A6. 総合順位の同点
- **場面**: §3.3 では、合計点が同じ人は同じ順位にする。そのあとの順位の数え方は決まっていない。
- **仮定**: 「1, 1, 3, 4」のように飛ばす数え方（自分より点が多い人数 + 1）にした。同点の人は席番号順に並べる。
- **理由**: 一般的な数え方のため。

### A7. 大富豪モードの設定一覧を engine に置く
- **場面**: 大富豪モードで選べるルールとおすすめ設定（§7）を、server と client の両方が使う。
- **仮定**: `DAIFUGO_MODE_RULE_IDS` と `DAIFUGO_MODE_DEFAULT_RULES` を engine から export する。表示名は持たない。
- **理由**: ルール ID の一覧なので、engine に置けば1か所で済む。

## B. 手の解釈

### B1. 組にも階段にも読めるカード
- **decisions §14.14 に反映済み**
- **場面**: 「♠5・ジョーカー・ジョーカー」は、5の3枚組とも、♠の階段とも読める。
- **仮定**: `play` 操作に `shape?: 'group' | 'run'` を持たせる。両方が出せる手として成り立つのに `shape` がなければ `ambiguousShape` エラーにする。片方しか成り立たないときは指定しなくてよい。`legalPlays` は形ごとに別の候補として返す。
- **理由**: engine が勝手に一方を選ぶと、プレイヤーの意図と違う手になるおそれがあるため。

### B2. 組の中のジョーカーのマーク
- **decisions §14.14 に反映済み**
- **場面**: §14.6 では、ジョーカーが「どの数字・どのマーク」の代わりかを記録する。組の中のジョーカーのマークは、縛りのとき以外は意味がない。
- **仮定**: 組の中のジョーカーは、縛りが成立しているときだけ、足りないマークをマーク順（♠・♥・♦・♣）に割り当てる。それ以外はマークを `null` にする。階段の中のジョーカーは、階段のマークにする。ジョーカーだけの組は、数字も `null` にする。
- **理由**: 意味のないマークを決めると、あとで縛りの判定に紛れ込むおそれがあるため。

### B3. 持っているカードの代わりにジョーカーを使う階段
- **場面**: ♠5・♠6・♠7 を持っているときに、「♠5・ジョーカー・♠7」として出せるかは決まっていない。
- **仮定**: 出せる。`legalPlays` もこの組み合わせを列挙する。
- **理由**: ジョーカーは「足りない数字の代わり」だが、手札から選んだカードの中で足りないなら代わりにしてよい。こうしておけば、画面でカードを選んだ時点で出せるかどうかが分かる。

### B4. カード ID の並び順（§14.9 の (5)、交換の同じ強さ）
- **場面**: §14.9 は「カード ID の並び順」で CPU の候補を並べるとしているが、その並びは決まっていない。
- **仮定**: 数字が弱い順（通常時。3→…→A→2）に並べ、同じ数字ならマーク順（♠・♥・♦・♣）、ジョーカーは最後（joker-0、joker-1 の順）とする。手札・出した手・捨て札のカードの並びもこの順にする。
- **理由**: §14.5 の上位の時間切れ（「同じ強さならマーク順」）と同じ順で、ID の文字列の順より自然なため。

## C. ルールの細部

### C1. スペ3返しを省く条件の「捨て札」
- **場面**: §6.2 では「スペードの3がすでに捨て札にあるときは、一周を行わない」とある。いまの場に出ているスペードの3（階段の一部など）が含まれるかは決まっていない。
- **仮定**: いまの場に出ているカードも「全員に見えている」ものとして扱い、省く条件に含める。
- **理由**: 場のカードも全員に見えていて、誰の手札にもないことが明らかなため。

### C2. スペ3返しに使えるカード
- **場面**: 4止めには「ジョーカーは代わりにできない」と明記されているが、スペ3返しには書かれていない。
- **仮定**: 返せるのは本物のスペードの3の1枚出しだけとする。もう1枚のジョーカーを「スペードの3の代わり」にはできない。
- **理由**: §6.5 に「スペードの3を1枚出すと」とあり、特定のカードの効果として読んだ。

### C3. 「スペードの3で上がっても反則にならない」の範囲
- **decisions §14.14 に反映済み**
- **場面**: §6.5 では、スペードの3で上がっても反則にならない。一方で、強さが逆のときに、ふつうの手番で最後にスペードの3（いちばん強い数字の1枚出し）を出す場合は、§6.9 の反則に当たる。
- **仮定**: 反則にならないのは、返しの一周で返したときだけとする。ふつうの手番では、§6.9 の判定どおり反則になる。
- **理由**: §6.5 の文は返しの一周の節にあり、§14.3 でも「返しの一周で…上がるのは反則ではない」と書かれているため。

### C4. ジョーカー2枚組の即流し（decisions §14.14 で決定。仮定を変更）
- **場面**: §2.5 は、ジョーカーの1枚出しに返す手段がないときだけ、すぐ場を流すと決めている。ジョーカー2枚の組も何にも負けない。
- **決定**: ジョーカーだけの手（1枚出し・2枚組）は、返しの一周がなければすぐ場を流す（理由 `jokerUnbeatable`）。返しの一周に入るのは1枚出しだけ。
- **経緯**: 当初は「2枚組は即流ししない」と仮定していたが、§14.14 で変更された。

### C5. 返しの手と、出したあとの効果
- **場面**: 返しの一周で返した手に、8切り・革命・縛りの成立などを起こすかは決まっていない。
- **仮定**: 返した手には、手番で出した手の効果（`afterPlay`）を起こさない。返しのあとの流れは、返しのルール（`onReturned`）が決める。返しの一周を始めるのも、手番で出した手のときだけ。
- **理由**: スペードの3の1枚出しは、その1のどのルールの効果にも当たらない。その2の4止め（4の2枚は捨て札になる）とも合う。

### C6. 縛りの成立の基準
- **場面**: §6.6 の「続けて出されたら」が、何と何を比べるのかは決まっていない。
- **仮定**: いまの場で直前に出された手と、新しく出した手を比べる。縛りは、一度成立したら場が流れるまで続く。
- **理由**: 文章のとおりに読んだ。

### C7. 都落ちと「最後の1人」の確定の順番
- **場面**: 1位が確定して都落ちが起きると、同時に残りが1人になることがある。
- **仮定**: 1位の確定 → 都落ち（`onFirstPlace`）→ 残りが1人なら確定、の順に処理する。都落ちした人の手札は捨て札にして公開する。最後の1人の手札は、手札に残したまま公開しない。
- **理由**: どちらの順でも順位は同じになる。都落ちは「確定した瞬間」に起きるので先にした。

### C8. 1位が確定した瞬間の手札枚数
- **場面**: 特権枠の判定に使う「1位が確定した瞬間の手札枚数」を、都落ちで手札が捨てられる前と後のどちらで数えるかは決まっていない。
- **仮定**: 都落ちの処理より前に、4席分の枚数を `firstPlaceHandCounts` に記録する。
- **理由**: 「上がった瞬間」の枚数なので。その1では記録するだけで使わない。

### C9. 返しの一周で返した人の扱い
- **場面**: 返したあとの「最後に出した人」が誰かは決まっていない。
- **仮定**: 返した人を「最後に出した人」にする（返した手は場に置く）。スペ3返しでは、そのあとすぐ場が流れる。
- **理由**: その1では結果に影響しない。その2の4止めは返しのモジュール側で扱える。

### C10. 返しの一周を省く判定の時点（decisions §14.14 で決定）
- **場面**: 出した手で1位が確定して都落ちが起き、都落ちした人の手札にあったスペードの3が捨て札として公開されることがある。
- **決定**: 省く条件は、出した直後ではなく、一周を始める直前の最新の状態で評価し直す（モジュールのフック `canStartReturnRound`）。省いた場合は、返す手段がないジョーカーの1枚出しとして、すぐ場を流す（`onReturnRoundSkipped`）。
- **補足**: 一周を始める時点では残っている人が2人以上いるので、参加者が0人になることはない。`runFlowEffects` の参加者0人の分岐は、防御のために残している。

## D. 時間切れ・CPU

### D1. 親の時間切れで、反則にならない1枚出しがないとき
- **decisions §14.14 に反映済み**
- **場面**: §8 では、親が時間切れになると「1枚出しのうちいちばん弱いカード」を出す。ただし、反則上がりになる手は、ほかに出せる手がある限り選ばない。反則にならない1枚出しがないときに何を出すかは決まっていない。
- **仮定**: 反則にならない1枚出しがなければ、CPU の並べ方（§14.14 で差し替えた §14.9）で先頭の手を出す。反則にならない手が先頭に来るので、そういう手があればそれを、なければ反則の手を出す。出せる手が1つもなければパスする（§2.4）。
- **理由**: 「ほかに出せる手がある限り選ばない」を、1枚出しに限らない意味で読んだ。

### D2. CPU の並べ方（decisions §14.14 で §14.9 を差し替え）
- **場面**: 元の §14.9 の並べ方を文字どおりに使うと、CPU は「3＋ジョーカー」のように、ジョーカーを弱い数字の組の水増しに使うことがよくあった。
- **決定**: 2番目の基準に「ジョーカーを使わない手を先に」を入れた。並べ方は、反則にならない手 → ジョーカーを使わない手 → いちばん弱いカードが弱い順 → 枚数の多い順 → 組を階段より先 → カードの並び順。親の時間切れで、反則にならない1枚出しがないときも、この並びを使う。

### D3. 交換で、ジョーカー同士が同じ強さになるとき
- **decisions §14.14 に反映済み**
- **場面**: §3.2 では、同じ強さのカードが複数あって決まらないときは下位が選ぶ。ジョーカー2枚を持っていて1枚だけ渡す場合も「同じ強さ」に当たる。
- **仮定**: ジョーカー同士は区別しないので、選ばせずに ID の順（joker-0 から）で自動的に渡す。
- **理由**: どちらを選んでも結果が同じ選択を、プレイヤーに求めないため。

## E. 見える情報

### E1. 交換フェーズの待ち
- **場面**: 下位に選択の余地があるかどうか（＝同じ強さのカードを複数持っているか）は、待ち（`awaiting`）として全員に見える。
- **仮定**: そのまま公開する。見える情報のテストでも、交換フェーズは比較の対象から外した。
- **理由**: §14.5 で「選択の余地がないときは待たずに渡す」と決めたので、避けられない。漏れるのは「下位の上位数枚に同じ強さのものがある」ことだけ。

### E2. 都落ちした人の手札
- **場面**: 都落ちした人の手札は全員に公開される（§4.1）。そのため、見える情報のテストで非公開の手札を入れ替えると、都落ちの出来事の中身が変わる。
- **仮定**: 決まりどおり公開する。テストでは、都落ちが起きた手のあとの比較を省いた。
- **理由**: ルールで決まっている公開なので、情報の漏れではない。

## F. その2（design-2 §2、§6）で置いた仮定

### F1. 「その1と同じ動きの検査」の記録の置き方
- **場面**: design-2 §2.9 は、変更前の engine で記録を作り、変更後も完全に一致することを確かめるよう求めている。記録を作る手順はテストの中に残す。
- **仮定**: `src/compat.test.ts` が、定番8種だけの6通りの組み合わせ × 3つの種（cpu、うち2つの種は決まった乱数で操作を選ぶ mixed も）の試合を最後まで進め、出来事の列と最後の状態の要点（得点、結果、乱数の状態、待ちと出来事の通し番号、操作の数）を `src/compat/*.jsonl` と比べる。比べるのは vitest のファイルスナップショット（`toMatchFileSnapshot`）。作り直すときだけ `-u` を付けて実行する（手順はテストの先頭に書いた）。
- **理由**: engine には `@types/node` がなく、テストからファイルを読み書きする手段を足すとパッケージが増えるため。1行に1つの出来事にして、違ったときに差分が読めるようにした。注意として、記録のファイルを消して実行すると、CI 以外では新しく書き出される（vitest の決まり）。

### F2. 既存のテストを書き換えた箇所（design-2 §6.4）
- `config.test.ts`「その2の8種は未実装としてエラーになる」→「16種すべてを受け付け、前提を満たさない組み合わせ（4止めだけ ON）は missingRequirement」に書き換えた。仕様が変わったため。
- `config.test.ts`「大富豪モードの選べるルールとおすすめ設定」: 大富豪モードの一覧を、実装済みの一覧と比べる形から、定番8種の並びそのものと比べる形にした。カスタムモードの一覧（16種）も確かめる。
- `config.test.ts`「定番8種は個別に ON/OFF できる」と `autoplay.test.ts` の256通り: 列挙の元を `IMPLEMENTED_RULE_IDS` から `DAIFUGO_MODE_RULE_IDS` に変えた（並びは同じなので、列挙される組み合わせもその1と同じ）。
- `errors.test.ts`「でたらめな対戦の途中に不正な操作を混ぜても…」: ルールを選ぶ元を `DAIFUGO_MODE_RULE_IDS` に変えた。16種から選ぶと、8切りなしの4止めで試合が作れなくなるため。定番8種の並びは同じなので、乱数の引き方も選ばれるルールもその1と同じ。16種の組み合わせは `scenarios2.test.ts` に新しく足した。
- `visibility.test.ts`「非公開の手札を入れ替えても…」: design-2 §2.9 のとおり、「その席が知っているカード」（自分に配られた・交換と7渡しで渡した／受け取った・場に出た・10捨てと都落ちで公開されたカード、ダイヤの3の義務が残っている間のダイヤの3）を除いたカードだけを入れ替える形に直した。ルールは16種から選ぶ（4の倍数の回は16種すべて）。7渡しの選択の待ちと、7渡しが起きたことも確かめる。
- 期待値は変えずに、入力のルールが16種になったテスト: `json.test.ts`、`purity.test.ts`、`hand.test.ts`（偶数の回）、`autoplay.test.ts`「全ルール ON で種を変えて…」、`visibility.test.ts` の「viewFor は他人の手札・乱数の状態を含めない」。どれも `IMPLEMENTED_RULE_IDS` をそのまま使っていて、テストのコードは変えていない。定番8種の挙動は F1 の検査で確かめている。
- `test/helpers.ts`: 場面を作る `scene` に `orderReversed` と `openingCard` の任意の指定、新しい状態の初期値（`seqLock: null` など）、`Driver.choose`、でたらめな操作の `choice`（0〜max 枚）、待ちの種類の記録（`RunStats.awaitKinds`）を足した。既存の場面の作られ方は変わらない。

### F3. `choose` の拒否のエラーの種類
- **場面**: design-2 §2.1 は `invalidChoice` を足すとだけ書いている。
- **仮定**: カードの重複と上限を超えた枚数は `invalidChoice`、手札にないカード（知らない ID を含む）は `cardNotInHand`、配列でないものは `malformed`、選択の待ちでない待ちへの `choose` は `wrongAwaitKind`。古い待ち番号・他人の席はほかの操作と同じ（`staleAwait`、`notYourAwait`）。
- **理由**: `play` や `exchangeGive` と同じ分け方にそろえた。

### F4. 中心の処理がルール ID で分けないためのモジュールの項目
- **場面**: 7渡しと10捨ては、選んだカードの行き先だけが違う。ダイヤの3スタートは `gameStart` の `leaderRule` を `'diamond3'` にする。design-2 §2.3 のフックの一覧には、これを表す項目がない。
- **仮定**: `RuleModule` に `choiceTarget?: 'give' | 'discard'` と `leaderRule?: LeaderRule` を足した。中心の処理は `handChoice` の `rule` のモジュールの `choiceTarget` で、渡す相手を決めるかどうかと行き先を決める。`leaderRule` は、有効なモジュールのうち最初に持っているものの値を使う。
- **理由**: 中心の処理に `rule === 'give_on_7'` のような分岐を置かない（その1の流儀）。

### F5. 激縛りの細部
- **連番の更新**: 激縛り中に組が出たら、その組の有効な数字（`groupRank`）で連番を進める。砂嵐（激縛りを無視する）が出た場合も同じく進めるが、すぐ場が流れて解除されるので結果に影響しない。
- **砂嵐で激縛りが成立する場合**: 強さが逆のとき、マークの組み合わせが同じ「4の3枚組 → 3の3枚組（砂嵐）」は激縛りの成立の条件にも当たる。このときは `seqLock` の出来事を出したあと、砂嵐で場が流れる（マーク縛りが8切りの直前に成立する場合と同じ扱い）。
- **枚数**: 激縛りの制限では、マークの組み合わせが合うことに加えて、枚数が縛りのマークの数と同じことも確かめる（場の枚数の制限と同じ結果になる。砂嵐は両方を無視する）。
- **ジョーカーを混ぜた組のマーク**: マーク縛りが OFF でも、激縛り中はジョーカーに足りないマークを割り当てて記録する（マーク縛りがすでに割り当てていれば、そのまま）。ジョーカーだけの手には、必要な数字とマークを割り当てる（`GroupPlay.rank` は null のまま）。
- **理由**: §16.1 の「ジョーカーは必要なカードの代わり」を、記録にもそのまま残すため（§14.6）。

### F6. 4止めの返しの候補の並び
- **仮定**: 手札の本物の4を決まった並び（マーク順）にしてから、2枚の組み合わせを作る。
- **理由**: `respond` の操作はカードを並べ直して候補と比べるため、候補も同じ並びにしておく必要がある（場面を直接作るテストでは手札が並んでいないことがある）。

### F7. K スキップの出来事
- **仮定**: `skipped` の `by` は手を出した人。出来事は、手番を始める（または場が流れる）直前に1回だけ出す。全員を飛ばして場が流れるときは `skipped` → `fieldCleared` の順。上がる手の場合は `placed` → `skipped` の順。
- **理由**: 効果の処理の順（上がりの判定 → スキップ → 手番を送る）のとおり。

### F8. 7渡し・10捨ての CPU と時間切れ
- **仮定**: CPU は、その時点の強さの向きで弱いカードから `max` 枚まで（手札が少なければ全部）手放す。同じ強さはカードの並び順、ジョーカーは最後。時間切れは0枚。手札をすべて手放すことになっても、そのまま手放して上がる。
- **理由**: §6.13「いちばん弱いカードから上限まで手放す」、design-2 §2.6 のとおり。上がれるなら上がるほうが CPU として自然。

### F9. 7渡しの相手が見つからない場合
- **場面**: 相手は「進行方向で次の、まだ上がっていない人」だが、見つからない場合の決まりはない。
- **仮定**: 起きない（選択の待ちを作るのは、出した人の手札が残っていてゲームが続いているときだけで、そのときは残っている人が2人以上いる）。型の上では、見つからなければ `to: null` になり、捨て札へ置く扱いになる。
- **理由**: 防御のための分岐。

### F10. 見える情報の「知っているカード」
- **場面**: ダイヤの3スタートでは、最初の1手が出るまで、親（全員に見える）がダイヤの3を持っていることが全員に分かる。
- **仮定**: 見える情報のテストでは、義務が残っている間のダイヤの3を「知っているカード」として扱い、入れ替えない。
- **理由**: ルールそのものが公開している情報なので、漏れではない。

### F11. モジュールの登録順
- **仮定**: その2の8種は、その1の8種の後ろに足した（4止め、激縛り、ダイヤの3スタート、砂嵐、7渡し、9リバース、10捨て、K スキップ）。解釈の補い（`refinePlay`）はマーク縛り → 激縛りの順になる。
- **理由**: 定番8種だけの試合で、モジュールの問い合わせの順が変わらないようにするため。効果は優先順で並べ直すので、ほかの順は結果に影響しない。
