# server 実装時に置いた仮定

> `packages/server`（その1）を実装する中で、`decisions.md`・`design.md` に答えがなかった場面、または解釈に迷った場面の記録。
> 各項目は「場面 / 置いた仮定 / 理由」の順に書く。遊んでみて、あるいはレビューで見直してよい。

## A. 席・ホスト・試合の区切り

### A1. ホストが移る時点
- **場面**: decisions §9 は「ホストが代役に切り替わったら（切断から10秒後）」移るとしている。design §4.6・decisions §14.11 は「切断の検出」のときにも確かめ直すとしている。
- **仮定**: 「接続中の人間」を「人間で、代役に切り替わっていない人」と読む。切断してから猶予（10秒）の間はホストのままで、代役に切り替わった時点で、接続中の人間のうち席順で次の人に移す。確かめ直す時点は design のとおり、すべての接続の変化。接続中の人間が1人もいないときは移さない（戻ってきた人がいれば、その時点で移す）。ホストが戻ってきても、ホストは元に戻さない。
- **理由**: ルールの正は decisions。猶予の間にすぐ戻る人からホストを取り上げないため。
- **decisions §14.15 に反映済み**（実装のままで正しいと決まった）。

### A2. 回数つき試合の最後と「もう一度」
- **場面**: engine の仮定 A5 により、回数つきの試合は最終ゲームのあと `gameResult` を経ずに `matchResult` へ移る。「同じメンバーでもう一度」（decisions §3.3）の進め方は決まっていない。
- **仮定**: `rematch` はホストだけが `matchResult` のときに送れる。ロビーには戻さず、同じ席（人間・CPU・代役中の人もそのまま）と同じ設定で、新しい種・新しい試合の識別子の試合をすぐ始める。点数と階級は engine の新しい試合として初期化される。操作の記録は新しい試合の分に入れ替える。
- **理由**: 「同じメンバーで」「点数と階級をリセットして続けられる」をそのまま形にした。ルールを変えたい場合は新しいルームを作る。

### A3. 途中参加できる時点
- **場面**: decisions §9 は「ゲームとゲームの間」に CPU の席へ入れるとしている。試合の結果画面（`matchResult`）が含まれるかは決まっていない。
- **仮定**: `gameResult` と `matchResult` の間は、はじめから CPU の席（席の種類が `cpu`）に入れる。席番号の小さい順に割り当て、その席の点数と階級を引き継ぐ。代役中の人間の席には本人以外は入れない。交換中・対戦中に新しい人が `hello` を送ると `cannotJoin`、入れる席がなければ `roomFull` を返し、接続をコード 4002 で閉じる。
- **理由**: 試合の結果画面も「ゲームの合間」で、次の `rematch` から遊べるため。

### A4. ロビーで切断した人の席
- **場面**: ロビーで切断した人の席を空けるかどうかは決まっていない。
- **仮定**: 空けない。試合中と同じく、猶予がたつと代役の扱い（`away`）になり、ホストなら移る。そのまま開始されたら、その席は代役（CPU）が操作し、本人が戻れば本人に戻る。追い出す操作はない。
- **理由**: 再読み込みで席を失わないことを優先した。友達同士の遊びで、知らない人が席を取り続ける場面は少ないと考えた。

### A5. 名前の更新
- **場面**: 同じ本人確認の値で戻ってきた人が、別の名前で `hello` を送ってきた場合。
- **仮定**: ロビーの間は新しい名前に更新する。試合が始まったあとは無視する。
- **理由**: 試合中に名前が変わると、ログや結果の表示が分かりにくくなるため。

### A6. 試合に対する操作の識別（decisions §14.15）
- **場面**: engine は試合ごとに待ち番号を1から振り直すので、`rematch` をまたいで前の試合に向けた操作が届くと、新しい試合の同じ番号の待ちに誤って当たり得る。
- **仮定**: `action`・`nextGame`・`endMatch`・`rematch` に `matchId`（`state.matchId`）を必須にする。付いていなければ `badMessage`、試合がなければ `wrongPhase`、現在の試合と違えば `staleMatch` で拒否する。`rematch` には終わった試合の `matchId` を付ける。この確認はホストかどうかの確認より先に行う。
- **理由**: 古い操作を、待ち番号の偶然の一致で通さないため。

### A7. CPU の名前
- **仮定**: 開始時に空席を CPU にするとき、名前を「CPU 席番号+1」（例：`CPU 2`）にする。表示名は client が差し替えてよい。

## B. 期限・代役・一時停止

### B1. 切断してから代役になるまでの手番
- **場面**: 切断を検出してから10秒の猶予の間に、その人の手番の期限がどうなるか。
- **仮定**: 猶予の間は人間の秒数のまま数える。この間に期限が切れたら `timeout` の方針で自動操作する。代役に切り替わった時点で、その席の待ちの期限を約1秒後（`cpuDelayMs`）に付け直し、以後は `cpu` の方針にする。
- **理由**: design §4.6 のとおり。猶予は「まだ戻ってくるかもしれない人」の扱い。

### B2. 猶予の間に戻ってきた人の期限
- **場面**: design §4.6 の「復帰：期限を秒数いっぱいに付け直す」が、代役に切り替わる前に戻った場合にも当てはまるか。
- **仮定**: 当てはめる。戻ってきた本人の待ちは、代役の前でも後でも秒数いっぱいに付け直す。
- **理由**: 復帰の処理を1つにするため。延ばせる時間は猶予の分だけで、design §4.6 で許容している。

### B3. 一時停止の範囲
- **場面**: 「人間の接続が0になったら一時停止」が、ロビーや結果画面にも当てはまるか。作っただけで誰も来ないルームをどうするか。
- **仮定**: すべての段階で当てはめる（ロビーで全員いなくなっても30分で消える）。ルームを作った時点を「一時停止」として始め、最初の人が `hello` を送ると再開する。誰も来なければ30分後に消える。席のない接続（`hello` 前）は人間の接続として数えない。
- **理由**: 使われないルームのストレージを残さないため。

### B3a. 一時停止の失効（decisions §14.15）
- **仮定**: 一時停止から `pausedCloseMs`（30分）を過ぎた時点で失効とする。削除のアラームがまだ処理されていなくても、新しい接続（fetch）・メッセージ（hello を含む）・切断の通知の処理の最初に失効を確かめ、失効していればその場でルームを閉じて消し（接続はコード 4003 で閉じる）、新しい接続には 404 を返す。再開はさせない。

### B4. 一時停止中の猶予
- **場面**: 一時停止している間に、切断した人の10秒の猶予が過ぎた場合。
- **仮定**: 一時停止中も猶予は数え、過ぎた人は代役の扱いにする（その席の待ちの残り時間は約1秒にする）。一時停止中のアラームは30分後の1つだけなので、この切り替えは次の入力（誰かが戻ってきたとき）の処理でまとめて行う。再開したとき、戻ってこない人の席は代役が操作する。戻ってきた人の席は秒数いっぱい、それ以外の人間（猶予の間にいる人）の席は止めた時点の残り時間で再開する。
- **理由**: 全員不在のあとに1人だけ戻った場合に、戻らない人の30秒を待たせないため。
- **decisions §14.15 に反映済み**（代役になった席の待ちは約1秒、残り時間で再開するのは代役になっていない席だけ、戻った本人は秒数いっぱい）。

### B5. 期限切れの処理を行う時点
- **場面**: decisions §14.10「期限を過ぎていても、時間切れの自動操作が実行される前に届いた本人の操作は受け付ける」。
- **仮定**: 期限切れの待ちへの `auto` は、アラームの処理の中でだけ送る。メッセージや接続の処理のついでには送らない。同じアラームで複数の期限が切れていれば、待ちの番号の小さい順に処理する。
- **理由**: アラームより先に届いた本人の操作を、そのまま受け付けるため。

### B6. アラームの処理で例外が起きたとき
- **仮定**: 例外は捕まえずに投げ直し、プラットフォームのやり直し（指数的に間隔をあけて最大6回）に任せる。保存は行わないので、状態は例外の前のまま。やり直しが尽きてアラームがなくなった場合は、次の入力の処理で設定し直す。保存された `alarmAt` と実際のアラームがずれるのは「`alarmAt` の時刻を過ぎた（鳴ったが処理に失敗した）」場合だけなので、`commit` は、計算した次の時刻が `alarmAt` と違うときに加えて、その時刻が現在以前のときも必ず設定し直す。起動時の点検（constructor）は、実際のアラームを `getAlarm()` で読んで比べる。
- **理由**: 原因が続く例外で1秒ごとに起き続けないようにするため（自前のやり直しはやめた）。

## C. 接続と応答の確認

### C1. 応答がない接続の判定
- **場面**: design §8.2 は、最後に自動応答した時刻で判定するとしている。
- **仮定**: 「最後に自動応答した時刻」と「最後にメッセージを受け取った時刻（接続した時刻を含む）」の遅いほうから `heartbeatTimeoutMs`（15秒）たった接続を、コード 4000 で閉じて切断として扱う。
- **理由**: 接続した直後はまだ自動応答の時刻がない（null）ため。操作のメッセージも生きている印になる。

### C2. 応答を確かめる時点
- **場面**: design §8.2 は「すでに鳴るアラームのとき、人間の操作を待ち始めて15秒後、結果画面でホストを待っている間の15秒ごと」としている。
- **仮定**: どの入力（メッセージ・接続・切断・アラーム）の処理でも確かめる。加えて、次の間は15秒ごとのアラームで確かめる（待ち始めて15秒後の1回だけでなく、60秒の交換の途中も繰り返す）。
  - 接続中の人間の操作を待っている間
  - ゲームの結果画面・試合の結果画面の間
  - ロビーで接続中の人間がいる間（decisions §14.15）
  - 席のない接続（hello 前）がある間（一時停止中を含む）
- **理由**: 起きているついでの確認は費用がかからない。交換の60秒の間に黙って切れた人を、待ちの途中でも見つけるため。

### C3. 開発サーバーの再起動・休止で消えた接続
- **場面**: Durable Object が作り直されると、切れた接続の `webSocketClose` は届かない。
- **仮定**: 入力の処理のたびに、席の「現在の接続の番号」と、開いている接続の添付データを突き合わせる。接続中のはずの席に対応する接続がなければ、その時点で切断を検出したことにする。起動時（constructor）には、保存された状態から次のアラームを計算し直し、ストレージのアラームと違えば設定し直す。
- **理由**: design §8.2「起動時の点検」と「接続の世代」のとおり。

### C4. 席が決まる前の接続
- **場面**: WebSocket をつないでから `hello` を送るまでの間。
- **仮定**: つないだ時点で、席なし（`seat: null`、`view: null`、出来事なし）の `state` を送り、以後もルームの変化のたびに送る（ロビーの名前や満員かどうかを見せるため）。中身は許可した項目だけのルーム情報と期限だけ。応答がなければ同じく閉じる（C2 のとおり、席のない接続がある間は定期的に確かめる）。
  - ローカルの開発サーバーでは、一度も送信していない接続をサーバーから閉じると、サーバー側では閉じた扱いになるが、クライアントの close が完了しない（CLOSING のまま）ことを確認した。1回でも送信した接続は正しく閉じる。client は接続直後に ping か hello を送るので、実害はない。1つのルームに同時に開ける接続は、`hello` 前を含めて12本まで（超えると 503）。
- **理由**: 名前入力の画面で、入れるかどうかを先に見せるため。

### C5. Origin の確認
- **場面**: design §4.5「接続時に Origin が自分のサイトであることを確かめる」。Node などブラウザ以外は Origin を付けないことがある（Node 22 の WebSocket は付けないことを確認した）。
- **仮定**: 2つの条件に分けて扱う。
  - **Origin が付いているとき**：scheme・ホスト・ポートを含む origin がリクエストの origin と一致するときだけ通す（違えば 403）。WebSocket の経路では、Upgrade の確認より先に行う。
  - **Origin が付いていないとき**：通す。
  - `POST /api/rooms` も同じ。
  - wrangler dev のプロキシは、自分のホストに一致する Origin の scheme を上流の scheme に書き換えて Worker に渡す（`https://127.0.0.1:ポート` が `http://...` で届くことを確認した）。そのため scheme だけの違いは開発サーバー越しには試せず、比較の関数（`src/origin.ts`）の単体テストで確かめている。
- **理由**: Origin の確認はブラウザ経由の他サイトからの接続を防ぐためのもので、ブラウザ以外は Origin を自由に付けられるため、無いものを拒否しても守りにはならない。client を別のオリジンで動かす場合は、許可するオリジンの設定を足す必要がある。

### C6. 本人確認の値と名前の形
- **仮定**: 本人確認の値は `[A-Za-z0-9_-]` の22〜64文字（128ビットを base64url にすると22文字）。保存するのは「固定の接頭辞＋値」の SHA-256（16進）だけ。名前は NFC に正規化し、前後の空白を除いて連続する空白を1つにしたうえで1〜12文字。制御文字・書式文字・私用領域・サロゲートの片割れ・行区切り・段落区切りは拒否する。名前の重複は許す。受け付けるメッセージは4096文字まで。
- **理由**: スマホの縦画面で4人分の名前を並べるため、名前は短めにした。

## D. 保存

### D1. 操作の記録の置き場所（design §8.2 の「1つの値」からの逸脱）
- **場面**: design §8.2 は、ルームの状態・期限・出来事の記録を1つの値にまとめるとしている。操作の記録（§8.2）も同じ値に入れると、無制限の試合で伸び続け、キーと値の合計 8MB の上限に届きうる。
- **仮定**: ルームの状態・期限・現在のゲームの出来事は1つの値（キー `room`）にまとめる。操作の記録だけは、ゲームごとに別のキー（`actions:ゲーム番号`）に分ける。どちらも同じ入力の処理の中で、間に `await` を挟まずに書くので、まとめて1回で反映される。試合の作成に使った設定と種は `room` の中に持つ。新しい試合（`start`・`rematch`）では古い記録を消す。
- **理由**: 1つの値の大きさを、1ゲーム分の出来事と状態だけに抑えるため。
- **残るもの**: 無制限の試合では、試合の状態の中の `match.results`（ゲームごとの順位と点の増減）がゲームごとに少量ずつ増える。1ゲームあたり百バイト程度で、現実的なゲーム数では上限に届かないので対策はしない（decisions §14.15）。テスト用の経路（`test/replay`）で、記録から試合を作り直すと保存された状態と一致することを確かめている。

### D1a. HTTP の本文の上限
- **仮定**: `POST /api/rooms` の本文は 2048 バイトまで。`Content-Length` が上限を超えていれば読まずに、付いていない（分割送信の）ときは読みながら数え、超えた時点で読むのをやめて 413 を返す。

### D2. メモリ上のキャッシュ
- **仮定**: ルームの状態はメモリに持たず、入力のたびに同期 KV（`ctx.storage.kv`）から読み直す。
- **理由**: SQLite バックエンドの同期 KV はその場で読めるため、キャッシュと保存の食い違いを考えなくて済む。休止・再起動で消えるものがない。

### D3. 状態の版番号と送る時点
- **場面**: design §4.5「変化があるたびに丸ごと送る」の「変化」に、応答確認の時刻やアラームの時刻のような内部だけの値の変化を含めるか。
- **仮定**: 含めない。席（種類・名前・接続中か・代役中か）、ホスト、設定、試合の状態、期限、一時停止のどれかが変わったときだけ版番号を上げて全員に送る。内部の値だけが変わったときは保存だけする。
- **理由**: 結果画面などで15秒ごとに同じ内容を全員に送らないため。

## E. テスト用の機能

### E1. 秒数の差し替えとテスト用の経路
- **仮定**: 開発サーバーに `--var CHOFUGO_TEST_MODE:1` を渡したときだけ、次を有効にする。`wrangler.jsonc` の `vars` には入れない（デプロイされるため）。無効のときは、本文の `timing` を 400、テスト用の経路を 404 にする。
  - `POST /api/rooms` の本文 `{ "timing": { ... } }`（各値はミリ秒の整数、10〜3,600,000）
  - `POST /api/rooms/:id/test/alarm`（アラームの処理をいま実行する。2回鳴った場合の確認）
  - `POST /api/rooms/:id/test/replay`（操作の記録から試合を作り直し、保存された状態と一致するか）
  - `POST /api/rooms/:id/test/instance`（Durable Object のインスタンスの識別子。休止から作り直されたかを確かめる）
  - `timing.testAlarmLagMs`（アラームを計算した時刻より遅らせて設定する。0〜60,000。本番は常に 0）。「期限を過ぎたが auto はまだ」「失効したが削除はまだ」の場面を作るために使う。
- **理由**: 本番の URL から第三者が秒数を変えられないようにするため。

## F. その2（カスタムモード）

### F1. setConfig の形と中身の境目（design-2 §3.1、§6.5）
- **場面**: §6.5 は「知らないモード、配列でない `rules`、型の違う値」を形の誤りとして拒否し、形が正しい値の中身だけを直すとしている。知らないルール ID の文字列と、重複した ID がどちらに当たるかは書いていない。
- **仮定**: 形の誤り（`badMessage`）として拒否するのは、`mode` がない・`daifugo`/`custom` 以外、`rules` が配列でない・文字列でない要素・16種にない ID・重複・17個以上、`gameCount` が 5/10/null 以外、知らないキー。直すのは「モードで選べないルール」「前提を満たさないルール」「並び順」だけ。形の検査はホストかどうかの確認より先に行う（その1と同じ。ホスト以外が形の正しい値を送ると `notHost`）。
- **理由**: その1では知らない ID と重複を拒否していた。拒否を減らす変更はモードと前提に関わるものだけにして、その1の検査を弱めないため。

### F2. 試合中のモード
- **仮定**: モードは engine の `MatchConfig` にないので、試合中の `room.config.mode` は設定の下書き（`draft.mode`）から出す。試合中は下書きを変えられないので、試合の設定と食い違わない。「もう一度」（`rematch`）でもモードはそのまま。

### F3. 保存の形式の番号（design-2 §3.3）
- **仮定**: ルームの値（キー `room`）の `v` が `2` でなければ（`v` がない値も含む）、失効したルームと同じ扱いにする。新しい接続には 404、開いている接続からのメッセージ・切断の通知・アラームでは、その場で接続をコード 4003 で閉じてストレージをすべて消す。起動時の点検（constructor）では何もしない（次の入力で閉じる）。
- **理由**: §16.6 のとおり形式の変換は作らない。起動時の点検の中で接続を閉じると、閉じる理由を送る前に作り直しが重なるおそれがあるため、閉じる処理は入力の処理に1つにまとめた。

### F4. 期限についての検査（design-2 §3.4）
- **仮定**: 入力の処理の最後（保存の直前、`commit` の最初）に、一時停止中でなければ「engine のすべての待ちに、期限の時刻（`at`）の付いた期限がある」「期限の一覧に、engine にない待ちが残っていない」を確かめる。テスト用の機能が有効なとき（`CHOFUGO_TEST_MODE=1`）だけ行い、見つかった問題をストレージ（キー `test:problems`、最大50件）に足して `POST /api/rooms/:id/test/check` で返す。本番では行わない。
- **理由**: テスト用の検査と書かれているため。通しの試合のテスト（大富豪・16種・CPU・7渡し）の最後に、問題が0件であることを確かめる。

### F5. テスト用の経路の追加
- **仮定**: `POST /api/rooms/:id/test/check`（F4）と `POST /api/rooms/:id/test/oldformat`（保存している値を古い形式の番号に書き換える。古い形式のルームの再現。その3からは番号 2 に書き換える）を足した。どちらもテスト用の機能が無効なら 404（`prod.test.mjs` で確かめる）。
- **追加（実装レビューを受けて、2026-11-17）**: 次の3つを足した。どれもテスト用の機能が無効なら使えない（本文の `seed` は 400、経路は 404。`prod.test.mjs` で確かめる）。
  - `POST /api/rooms` の本文の `seed`（0 でない値を含む uint32 の4つ）：試合の種を固定する。ルームの値には入れず、別のキー（`test:seed`）に置き、試合を作るとき（開始・「もう一度」）に使う。保存の形式（`STATE_FORMAT`）は変えない。種が決まると、1ゲーム目の流れは CPU・代役・時間切れの操作も含めて engine だけで再現できる（人間の席が決まった操作だけをする場合）。通しのテスト（`choice.test.mjs`）は `test/scenario.mjs` で engine を動かして必要な出来事が起きる種を探し、その種のルームで試す（でたらめな配りで出来事が起きるまで待たない）。交換のある2ゲーム目以降は同時の待ちの処理の順が届く順で変わりうるので、1ゲーム目だけを使う。
  - `POST /api/rooms/:id/test/storage`：保存の有無（ルームの値があるか、操作の記録のキーの数、キーの総数、アラームの時刻）。古い形式のルームを閉じたあとに、保存とアラームが消えたことを直接確かめる（`test/oldformat` の `{ ok: false }` は保存が残っていても false になるため）。
  - `POST /api/rooms/:id/test/timing`（本文は `timing` と同じ形の一部）：作ったあとのルームの秒数を差し替え、アラームを設定し直す。「期限を過ぎたが、まだ処理されていない」時点で `test/alarm` を2回呼ぶテスト（`chofugo2.test.mjs`）で、アラームを遅らせたまま次の待ちの期限だけを長くし、確認のあとに元へ戻すために使う。

### F6. テストのポート
- **仮定**: 通しのテストの開発サーバーは 19480〜19489、インスペクターはその +10（19490〜19499）を使う（`test/helpers.mjs` の `PORTS`）。
- **理由**: 同じ機械の別のプロジェクトと 8801 番が衝突してテストが落ちたことがあるため。

### F7. 手札の漏れの検査とダイヤの3
- **場面**: 通しのテストの `checkNoLeak` は、届いた値の中の他人の手札のカードを探す。ダイヤの3スタートでは `GameView.openingCard`（`diamond-3`）が全員に届く。
- **仮定**: `openingCard` の欄は検査から外す。7渡しで自分が渡したカードは、受け取った人の手札にあっても見えてよいものとして扱う（交換と同じ）。
- **理由**: 最初の親がダイヤの3を持っていることは、ルールで全員に分かる情報のため（engine の設計どおり。交換が終わるまでは null、design-2 §6.6）。

## G. その3（超富豪モード）

### G1. 超富豪モードの設定（design-3 §3.1）
- **仮定**: `setConfig` の `mode: 'chofugo'` は、`rules` の形（配列・知っている ID・重複なし）はその2と同じく確かめるが、中身は使わず16種すべてにする。`validateConfig` には `abilities: true` を渡して確かめる（都落ちが必須）。ゲーム数は選べる。超富豪モードから大富豪・カスタムへ切り替えたときは、16種を送られたものとして、その2と同じく直す。
- **理由**: 形の検査を弱めないため（その2の F1 と同じ）。

### G2. 試合の設定を作る処理（design-3 §6.6）
- **仮定**: `state.ts` の `buildMatchConfig` を、開始（下書きのモードから `abilities` を決める）と「もう一度」（終わった試合の `config` から `rules`・`gameCount`・`abilities` を引き継ぐ）の両方で使う。`matchInit.config` にも同じ値が入るので、操作の記録からの再現（`test/replay`）も同じ設定で作り直す。

### G3. 期限の引き継ぎ（design-3 §6.1）
- **仮定**: `syncDeadlines` は、消す前の期限の一覧を読んでおき、新しい待ちに `continues` があり、元の番号の期限が残っていて、同じ席で、その席が人間（代役でない）なら、元の `at` と `remaining` をそのまま写す。元の期限がすでに過ぎていても写す（すぐに時間切れの `auto` が新しい番号に出る）。元の期限が残っていない（アラームの処理で先に消した）ときは、ふつうの新しい待ちと同じく秒数いっぱい（CPU・代役は約1秒）にする。
- **理由**: アラームの処理で `auto` を出す CPU・代役は、期限を消してから `auto` を出すので、元の期限はいつも残っていない（約1秒になる）。人間の時間切れの `auto` は特権を使わない。

### G4. 選択の途中の保存の返事（design-3 §6.2）
- **仮定**: `selectAbilities` が成功したら、外へ見える内容が変わらなくても、送った接続にだけ `state` を送る（版番号は上げない、`eventsFull` は false、出来事はその入力で増えた分だけ）。`confirm: true` でも同じ扱い（確定すれば内容は変わるので、ふつうはほかの人にも送られる）。

### G5. 期限についての検査（design-3 §6.5）
- **仮定**: 検査は `match.game.awaiting`（状態の中の待ちの実体）と期限の一覧を突き合わせる。待ちのあるフェーズ（exchange・ability・play）だけを見る（結果の画面では engine が待ちを空にしており、期限も付けない）。待ちのあるフェーズで待ちが0なら「phase … has no await」を記録する。

### G6. 保存の形式の番号
- **仮定**: `STATE_FORMAT` を 3 にした（engine の `MatchState.version` も 3）。その2までに作られたルーム（番号 2）は、その2の F3 と同じく失効したルームとして扱う。

### G7. 手札の漏れの検査と特権
- **仮定**: 通しのテストの `checkNoLeak` は、透視で見た・見られたカード（`ability` の `cards`、`GameView.peek`）と、強奪で動いたカード（`given`・`taken`）を、当事者が知っていてよいカードに足す。当事者でない席にこれらの中身が届いたら問題にする。`UsableAbility.cards` も自分の手札の中だけであることを確かめる。

### G8. 通しのテストのでたらめな操作
- **仮定**: `helpers.mjs` の `chooseAction` は、特権の選択では1個以上を選び（特権が実際に使われるようにするため。0個の決定は client とボットで確かめる）、手番では半分の確率で使える特権をでたらめな引数で使い、スキップを付けられる手には半分の確率で付ける。知らない待ちの種類には例外を投げる（交換の分岐に落ちて黙って止まらないように）。

### G9. 受理した操作の印（`acceptedReqId`、design-2 §6.3）
- **場面**: client は「自分が送った操作が受理された」ときに7渡しで受け取ったカードの強調を消す。`state` には、どの入力で進んだかが入っていないので、「送信待ちの間に時間切れの `state` が届き、自分の操作は `staleAwait` で拒否された」場合と見分けられなかった（client-assumptions H11）。
- **仮定**: `StateMessage` に任意の項目 `acceptedReqId` を足した。engine が `action` を受け付けた入力の処理で、その操作を送った接続に送る `state` にだけ、その `reqId` を入れる（`reqId` のない操作には付けない）。ほかの人への `state`、拒否、時間切れ・CPU の自動の操作、ホストの操作（設定・開始・次のゲームなど）には付けない。受け付けた操作で外へ見える内容が変わらなかったときも、送った接続には `state` を送る（`acceptedReqId` 付き。ふだんは操作で内容が変わるので、増える送信はない）。
- **理由**: 届く順や出来事の中身から推しはかるより確実で、追加は任意の1項目だけ（古い client は無視する）。
