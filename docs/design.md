# 超富豪 — 設計書（その1：大富豪モード）

> 対象は `decisions.md` §10 の「その1」。ルールの中身は `decisions.md` が正で、この文書は「どう作るか」を決める。
> その2（カスタム）・その3（超富豪）・第2段階で足すものを、作り直しなしで足せる形にすることを条件にしている。

## 1. その1の範囲

**入れるもの**

- ルームの作成と参加（招待リンク、名前入力、同じ席への復帰）
- 4人対戦。空席と切断者の代役をする CPU
- 基本の対戦、カード交換、得点、試合の区切り（5・10・無制限）
- 定番8種：`flush_on_8`、`revolution`、`temp_reverse_on_j`、`spade3_beats_joker`、`suit_lock`、`runs`、`forbidden_finish`、`dethrone`
- 「返しの一周」（スペ3返しで使う）
- 制限時間、切断時の代役、ホスト権限の移動、一時停止、ゲームの合間の途中参加
- 大富豪モードのルール設定画面

**入れないもの**（構造だけ用意する）

- 残りの8種、カスタムモードの画面（その2）
- 特権と超富豪モード（その3）

## 3. engine

### 3.1 原則

- **純粋関数**。同じ状態と同じ操作からは、必ず同じ結果が出る。時計・乱数・通信に直接触れない。
- **乱数は状態の中に持つ**。試合を作るときにサーバーが種（128ビット）を渡し、engine は状態の中の乱数を進めながら使う。配り方、最初の人、CPU の選択、時間切れの自動操作がすべて再現できる。
- **時間は操作として入ってくる**。engine は秒数を知らない。サーバーが時間切れを検知して `auto` 操作を送る。
- **状態は JSON にそのまま保存できる形**。`Map`・`Set`・クラスのインスタンス・`undefined` の値を持たない。
- **例外を投げない**。不正な操作はエラーの結果として返す。
- **隠す情報の切り出しは engine の仕事**。状態も出来事も、席ごとに見える形へ変換する関数を engine が持つ。

### 3.2 公開する関数

```ts
// 試合を作り、1ゲーム目を配った状態を返す
createMatch(config: MatchConfig, seed: Seed): { state: MatchState; events: GameEvent[] }

// 操作を1つ適用する。不正なら error を返し、状態は変えない
applyAction(state: MatchState, action: Action): 
  | { ok: true; state: MatchState; events: GameEvent[] }
  | { ok: false; error: ActionError }

// いま誰の何の操作を待っているか（並行して複数あり得る）
awaiting(state: MatchState): Awaiting[]

// 席から見える状態（自分の手札、他人の枚数、場、自分に許される手）
viewFor(state: MatchState, seat: SeatId): PlayerView

// 席から見える出来事（見せてはいけない中身を落とす）
eventsFor(events: GameEvent[], seat: SeatId): VisibleEvent[]

// その席が出せる手の一覧（CPU・時間切れ・画面の暗転・テストで使う）
legalPlays(state: MatchState, seat: SeatId): LegalPlay[]
```

### 3.3 操作

| 操作 | 送る人 | 内容 |
|---|---|---|
| `play` | 手番の人 | カードを出す。反則上がりになる手は `confirmFoul: true` が必要 |
| `pass` | 手番の人 | パス。親は、出せる手が1つもないときだけ |
| `respond` | 返しの一周で聞かれている人 | 返すカード、またはスキップ |
| `exchangeGive` | 交換で選ぶ必要のある人 | 渡すカード |
| `auto` | サーバー | 待っている操作を自動で決める。`policy` は `timeout` か `cpu` |
| `nextGame` | サーバー（ホストの要求を受けて） | 次のゲームを配る |
| `endMatch` | サーバー（ホストの要求を受けて） | 無制限の試合を終える |

- 操作にはどの席のものかを必ず付ける。席と本人の対応はサーバーが確認し、engine は「その席がいま待たれているか」を確認する。
- `auto` は、engine が `awaiting` の1件に対して決まりどおりの手を選ぶ。`timeout` は `decisions.md` §8、`cpu` は §3.6 の決まりを使う。どちらも状態の中の乱数だけを使う。

### 3.4 状態の持ち方

```ts
type MatchState = {
  version: 1;
  config: MatchConfig;        // 有効なルール、ゲーム数、閾値
  rng: RngState;
  gameNo: number;             // 1 から
  scores: number[];           // 席ごとの合計点
  prevRanks: Rank[] | null;   // 前のゲームの階級（席ごと）
  phase: 'exchange' | 'play' | 'gameResult' | 'matchResult';
  game: GameState | null;
  nextAwaitId: number;        // 待ちの通し番号
  nextEventSeq: number;       // 出来事の通し番号
};
```

`GameState` に持つもの：

- 席ごとの手札、公開されている捨て札、場（いちばん上の手・出した人・この場で出た手の履歴）
- 手番、手番の向き、席ごとのパス状態
- 上から確定した順位の列と、下から確定した順位の列（強制最下位）
- 強さの向きを決める2つの状態（革命中か、J バック中か）
- 縛りの状態
- 待っている操作の一覧（§3.5）
- 1位が確定した瞬間の、席ごとの手札枚数（特権枠の判定用。その1では記録だけする）
- 交換の進み具合（交換フェーズのとき）

### 3.5 待ちの仕組み

「誰かの操作を待っている」ことを、手番・返しの一周・交換のすべてで同じ形で表す。その2の7渡し・10捨て・4止め、その3の特権選択も同じ形に乗せる。

```ts
type Awaiting = {
  id: number;                 // 通し番号。サーバーが制限時間と結び付ける
  seat: SeatId;
  kind: 'turn' | 'respond' | 'exchangeGive';   // 後の段階で種類が増える
  timer: 'turn' | 'respond' | 'choice' | 'exchange' | 'ability';  // どの秒数を使うか
};
```

- 交換フェーズでは複数の席を同時に待つ。それ以外は1席ずつ。
- 待ちが変わるたびに新しい `id` を振る。同じ人の手番が続く場合も、新しい手番は新しい `id` になる。
- 古い `id` への `auto` は無視する（時間切れと本人の操作が行き違っても壊れない）。

### 3.6 CPU の決まり（その1）

弱い CPU。`auto` の `policy: 'cpu'` で使う。

- **親のとき**：出せる手のうち、いちばん弱い数字の手を出す。同じ数字なら枚数の多い手を選ぶ。
- **親でないとき**：出せる手のうち、いちばん弱いものを出す。なければパス。
- **反則上がりになる手**は、ほかに選べる行動（パスを含む）がある限り選ばない。
- **返しの一周**：返せるなら必ず返す。
- **交換**：`decisions.md` §3.2 のとおり。

### 3.7 ルールの足し方

ルールごとに1ファイルのモジュールにし、中心の処理は「登録されたモジュールに問い合わせる」形にする。中心の処理に `if (ルールが ON)` を散らさない。

```ts
type RuleModule = {
  id: RuleId;
  requires?: RuleId[];                               // 前提のルール
  restrictPlay?(ctx, play): Violation | null;        // 出せる手を絞る（縛り、のちに独裁・号砲）
  extraPlays?(ctx): Play[];                          // ふつうは出せない手を出せるようにする（のちに砂嵐）
  afterPlay?(ctx, play): Effect[];                   // 出したあとの効果（8切り、J バック、革命）
  isFoulFinish?(ctx, play): boolean;                 // 反則上がりの判定
  onFirstPlace?(ctx, seat): Effect[];                // 1位が確定したとき（都落ち）
  onFieldCleared?(ctx): Effect[];                    // 場が流れたとき（縛り・J バックの解除）
};
```

- **効果は順番に処理する**。1手で起きた効果を列に積み、決まった順（革命 → 数字の効果 → 上がりの判定 → 場の流れ）で1つずつ処理する。プレイヤーの選択が必要な効果は、待ちを作って処理を止め、操作が来たら続きから再開する。再開に必要な情報は状態の中に持つ。
- **手の種類**（組・階段）の認識は、種類ごとの解析関数を登録する形にする。階段は `runs` が ON のときだけ登録する。
- **ルール ID と表示名は分ける**。engine はルール ID だけを使う。表示名と説明文は client の1つの表に置く（名前の調査結果は文字列の差し替えだけで反映できる）。
- その1で作るモジュールは8個。フックの種類は、その2以降で必要になったら足してよい。

### 3.8 隠す情報

**状態**（`viewFor`）

- 自分の手札は中身、他人の手札は枚数だけ。
- 捨て札・場・順位・得点・強さの向き・縛り・待たれている席は全員に見える。
- 自分が待たれているときだけ、出せる手の一覧（`legalPlays`）を含める。反則上がりになる手には印を付ける。
- 乱数の状態は含めない。

**出来事**（`eventsFor`）

出来事には、全員に見える部分と、一部の席だけに見える部分を分けて持つ。

| 出来事 | 全員に見えるもの | 当事者だけに見えるもの |
|---|---|---|
| 配る | 各席の枚数 | 自分の手札 |
| 交換 | 誰から誰へ何枚 | カードの中身（渡した人と受け取った人） |
| カードを出す・パス・場が流れる・革命など | すべて | なし |
| 都落ち | 捨てられた手札の中身 | なし |

その2以降の7渡し・強奪・透視も、この表に行を足して扱う。

### 3.9 テスト

- **ルールごとの単体テスト**：`decisions.md` の各節の例をそのままテストにする。
- **受け入れ基準**：仕様書 §11.1（基本対戦）、§11.3（都落ち）、§11.5 のうちその1に関係する項目。§11.2 の特権枠の計算関数も、単体では先に作ってテストする。
- **自動対戦テスト**：種を変えた多数の試合を、ルールの ON/OFF の全256通りを含めて CPU 同士で最後まで回し、毎手で次を確かめる。
  - 54枚が手札・場・捨て札のどこかにちょうど1枚ずつある。
  - 待たれている席には、選べる操作が必ず1つ以上ある。
  - 試合が決まった手数の中で終わる。
  - 順位は4席で重複がなく、1ゲームの得点の合計は0。
- **でたらめな操作のテスト**：不正な操作（他人の手番、持っていないカード、古い待ち番号）を混ぜても、状態が変わらずエラーが返る。
- **見える情報のテスト**：`viewFor` と `eventsFor` の結果を文字列にしたとき、他人の手札のカード ID が含まれない。

## 4. server

### 4.1 構成

- Worker が URL を見て振り分ける。`/api/*` だけを Worker が処理し、それ以外は静的ファイル（client）を返す。
- 1ルーム＝1 Durable Object（SQLite バックエンド）。ルーム内の処理は1つずつ順番に行われる。
- 接続は WebSocket の Hibernation API で受ける。

| URL | 内容 |
|---|---|
| `POST /api/rooms` | ルームを作る。サーバーが推測されにくいルーム ID を作って返す |
| `GET /api/rooms/:id/ws` | WebSocket 接続。作られていないルームには接続できない |

### 4.2 Durable Object の性質に合わせた決まり

公式ドキュメントで確認した性質：操作がない状態が約10秒続くと休止し、メモリ上の状態は消える。次の操作で作り直される。`setTimeout` を使うと休止できなくなる。

- **ルームの状態はすべてストレージに保存する**。操作を1つ処理するたびに、保存してから各席へ送る。メモリ上の値は、ストレージから読み直せるキャッシュとしてだけ使う。
- **接続と席の対応は、接続に付ける添付データ**（`serializeAttachment`）に持つ。休止から戻ったときに読み直す。
- **時間切れはアラームで扱う**。`setTimeout` は使わない。アラームは1つしか持てないので、いちばん近い期限に合わせて設定し、鳴ったら期限切れのものをすべて処理して、次の期限に設定し直す。

### 4.3 ルームの状態

- ルーム ID、作成時刻、段階（ロビー・試合中・終了）
- 席4つ：種類（人間・CPU・空き）、名前、本人確認用の値のハッシュ、接続中かどうか、切断した時刻
- ホストの席
- 設定の下書き（ロビーで変更中のルールとゲーム数）
- 試合の状態（engine の `MatchState`）
- 期限の一覧（待ち番号 → 期限の時刻）
- 現在のゲームの出来事の記録（復帰した人にログを見せるため）

### 4.4 本人の確認

- client が128ビットの乱数を作り、ブラウザに保存する。接続して最初に送る。
- サーバーはそのハッシュを席に結び付ける。同じ値で接続してきたら同じ席に戻す。
- この値はほかの人に送らない。URL にも含めない。
- 同じ席に2つ目の接続が来たら、古い接続を閉じる。

### 4.5 通信

JSON を WebSocket で送る。

**client から**：`hello`（本人確認の値と名前）、`setConfig`（ホスト、ロビー中）、`start`（ホスト）、`action`（`play`・`pass`・`respond`・`exchangeGive`）、`nextGame`・`endMatch`・`rematch`（ホスト）。

**server から**：`state`（ルームの様子、自分から見えるゲームの状態、新しい出来事、期限、サーバーの時刻）、`error`。

- **変化があるたびに、その席から見える状態を丸ごと送る**。差分は送らない。状態は小さく、復帰の処理が「最新を1回送る」だけで済む。
- 出来事には通し番号を付ける。client は番号で重複を除き、演出とログに使う。
- 受け取ったメッセージは、形・長さ・値の範囲をすべて確かめる。名前は長さと文字を制限する。大きすぎるメッセージは捨てる。
- 席を決めるのはサーバー。client が送る操作に席の指定は含めない。
- WebSocket の接続時に、`Origin` が自分のサイトであることを確かめる。

### 4.6 制限時間と CPU

- engine の `awaiting` が変わるたびに、新しい待ちに期限を付ける。
  - 人間の席：`decisions.md` §8 の秒数。
  - CPU の席と、切断して代役になっている席：約1秒（考えているように見せる短い間）。
- アラームが鳴ったら、期限切れの待ちに `auto` を送る。人間の席は `timeout`、CPU と代役は `cpu`。
- **切断**：接続が切れたら時刻を記録し、10秒後にも戻っていなければ代役に切り替える（その席の待ちの期限を約1秒後に付け直す）。
- **復帰**：本人の操作に戻し、その席に待ちがあれば期限を秒数いっぱいに付け直す。切断と再接続を繰り返して時間を延ばせることになるが、友達同士の遊びなので許容する。
- **全員不在**：人間の接続が0になったら期限をすべて止め、30分後のアラームを設定する。誰かが戻れば、止めた時点の残り時間で再開する。30分たったらルームを閉じてストレージを消す。
- **ホストの移動**：ホストが代役に切り替わった時点で、接続中の人間のうち席順で次の人をホストにする。

### 4.7 途中参加

- ゲームの結果画面の間だけ、CPU の席（はじめから CPU だった席）に新しい人が入れる。点数と階級を引き継ぐ。
- 切断中の人間の席には、本人以外は入れない。

### 4.8 テスト

- 4つの接続でルームを作り、1試合を最後まで進める通しのテスト（ローカルの開発サーバーに対して実行する）。
- 休止を挟んでも続けられること（メモリ上の状態を捨てて読み直す経路）。
- 時間切れ、切断から代役、復帰、ホストの移動、全員不在からの再開。
- 他人の席の操作、ホスト以外のホスト操作、壊れたメッセージが拒否されること。
- テストに追加のパッケージ（Workers 用のテスト実行環境など）が必要な場合は、足す前に相談する。

## 5. client

- 画面：ホーム、ロビー（名前入力・席・ルール設定・ゲーム数）、カード交換、対戦、ゲームの結果、試合の結果。
- 表示はサーバーから届いた状態をそのまま描く。client 側でゲームの結果を決めない。
- 出せないカードは暗くする。判断にはサーバーから届く「出せる手の一覧」を使う。
- 期限はサーバーの時刻との差を補正して残り時間を表示する。
- 接続が切れたら自動でつなぎ直す。
- **見た目は、画面を作る前に案を出して確認を取る**（`decisions.md` §11）。確認が取れるまでは engine と server を先に進める。

## 6. 作る順番

1. engine（テストと自動対戦テストを含む）
2. server（通しのテストを含む）
3. 見た目の案の確認 → client
4. Cloudflare に公開

各段階で、実装のレビューを通してから次へ進む。

## 7. 既知の割り切り

- 乱数は暗号用のものではない。自分の手札から種を逆算するのは現実的ではないが、理論上の保証はない。友達同士の遊びとして許容する。
- ルーム作成に回数の制限はない。公開して問題が出たら足す。
- ルーム ID を知っている人は誰でも入れる。合言葉などは付けない。
